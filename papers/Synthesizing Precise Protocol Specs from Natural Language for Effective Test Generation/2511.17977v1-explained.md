# Learning Guide: AutoSpec

## Paper at a glance

- **Title:** *Synthesizing Precise Protocol Specs from Natural Language for Effective Test Generation*
- **Authors:** Kuangxiangzi Liu, Dhiman Chakraborty, Alexander Liggesmeyer, and Andreas Zeller
- **Version:** arXiv:2511.17977v1, 22 November 2025
- **Source:** [2511.17977v1.pdf](2511.17977v1.pdf)
- **Prototype:** AutoSpec, short for "Author Utterances to Specifications"
- **Goal:** Convert natural-language Internet protocol RFCs into executable I/O grammars that can generate protocol tests and act as test oracles.
- **Main result:** Across five protocols, AutoSpec recovers an average 92.8% of client message types and 80.2% of server message types, with 81.5% average message acceptance on real implementations.

AutoSpec uses existing GPT-4-class models at inference time. It does not train a new model in the reported work.

## 1. Problem

Protocols are specified in RFC prose, grammar snippets, tables, examples, and normative rules. Humans must normally turn these documents into tests. Direct LLM test generation is hard to trust because it can hallucinate values, miss corner cases, and provide poor traceability.

AutoSpec asks an LLM to create a reusable formal specification instead of one-off tests. A deterministic grammar-based fuzzer then generates tests from that specification. This provides:

- an inspectable and version-controlled artifact;
- sentence-level traceability to RFC text;
- reproducible test generation without an LLM in the testing loop;
- an executable oracle for checking responses;
- a future corpus of natural-language/formal-specification pairs.

## 2. What is an I/O grammar?

An I/O grammar describes complete stateful interactions, not only isolated message syntax. Nonterminals carry party prefixes such as `Client:` or `Server:` to state who produces a message and when.

A POP3 grammar can express:

```text
Client sends USER
Server returns a USER response
Client sends PASS
Server enters TRANSACTION state
Client sends LIST with a valid message number
Server returns a LIST response
```

It can also attach semantic constraints, such as a message number being between 1 and 8. A fuzzer instantiates the grammar to produce concrete sessions.

## 3. Inputs, artifacts, and outputs

### External inputs

- RFC HTML document.
- Protocol implementation or system under test (SUT).
- Configuration: protocol target, model backend, ports, decoding settings, and repair limits.
- For evaluation, an expert-authored golden I/O grammar.

### Intermediate artifacts

- Cleaned RFC sections with section IDs and paragraph indices.
- Section classifications and actions.
- Structured JSON fragments containing states, commands, responses, transitions, syntax, and constraints.
- Section-local typed micrographs with provenance.
- Global state-transition multigraph.
- Structured RFC content index.
- Minimal transition paths (MTPs).
- Initial I/O grammar.
- Generated protocol tests and request-response traces.
- Parser/runtime failures.
- Structured repair reports and minimal patches.

### Final outputs

- Refined, executable I/O grammar.
- Traceability links from grammar elements and repairs to RFC sections/paragraphs.
- Deterministically generated protocol test sessions.
- Message- and trace-level conformance results.

## 4. End-to-end architecture

```text
RFC HTML
  -> clean and split into sections
  -> LLM classification and structured extraction
  -> LLM section-local graph synthesis
  -> deterministic global graph merge
  -> minimal transition paths + structured RFC content
  -> LLM I/O grammar generation
  -> schema and generatability checks
  -> Fandango test generation
  -> execution against SUT
  -> trace/error classification
  -> LLM minimal repair patch
  -> grammar regeneration and re-execution
  -> refined executable grammar
```

## 5. Stage 1: preprocess the RFC

### 5.1 Clean and split

A crawler removes boilerplate, tables of contents, and footers while preserving section and paragraph identifiers. It emits one JSON file per RFC section.

### 5.2 Filter sections

An LLM inspects each section and assigns:

- a semantic label: state machine, overview, example, or other;
- an action: extract, copy, or summarize;
- a summary of at most 30 tokens;
- the original section ID and paragraph anchors.

Only `extract` sections proceed to detailed extraction. `copy` and `summarize` remain context.

### 5.3 Extract structured elements

A second prompt extracts states, commands, transitions, response types, message syntax, constraints, and command dependencies into normalized JSON. Missing data becomes `null`, keeping the output total and machine-checkable.

Pydantic validates required fields, types, and ranges. On failure, AutoSpec discards the invalid instance and reissues the prompt once.

### 5.4 Synthesize section-local micrographs

Another LLM pass converts validated JSON into a typed local graph. It harmonizes names, merges near-duplicates, and recovers implied intra-section edges.

Nodes represent states, commands, and optional responses. Edges include:

- `invokes`: state to command;
- `yields`: command to state or response;
- dependencies later normalized to `requires` or `enables`.

A deterministic acceptance filter rejects nodes or edges with invalid types or missing provenance and resolves duplicates using precedence:

```text
normative RFC text > examples and overviews
```

### 5.5 Merge globally

The global merger is rule-based, not an LLM. It normalizes labels, canonicalizes edge types, unions nodes/edges, preserves provenance, propagates compatible constraints, and flags contradictions.

The resulting graph can be understood as:

```text
G = states + commands + typed edges + global constraint store
```

### 5.6 Compute minimal transition paths

For every target command or transition, AutoSpec finds the shortest valid edge sequence from an initial state that satisfies dependencies and preconditions and establishes the required postcondition.

For POP3, one path is conceptually:

```text
initial --USER--> initial --PASS--> transaction
        --STAT/LIST/DELE--> transaction --QUIT--> update
```

MTPs act as retrieval keys: each path identifies the smallest relevant set of RFC clauses and constraints.

### Preprocessing outputs

1. **Structured RFC Contents:** normalized states, commands, constraints, and provenance.
2. **State-Transition Paths:** compact, dependency-resolved protocol progressions.

## 6. Stage 2: synthesize the I/O grammar

The Grammar Generator Agent performs five operations.

1. **Path to FSM skeleton:** Convert each MTP into state-command-transition triples and decide exchange order and nonterminals.
2. **Evidence alignment:** Retrieve the exact RFC clauses and message listings needed by the skeleton.
3. **Constraint enrichment:** Attach range, length, equality, and functional constraints as `where` clauses.
4. **Normalization:** Create `<start>`, group productions, deduplicate commands, normalize aliases, and include terminals.
5. **Patch integration:** Apply repair-agent changes as minimal diffs while preserving provenance, then rerun checks.

The Figure 6 prompt specifies task, inputs, grammar rules, workflow, and the instruction to output raw grammar only. Guardrails require literal RFC symbols, section-local scope, normative precedence, provenance, schema validity, and MTP generatability.

## 7. Stage 3: generate and execute tests

Fandango instantiates the I/O grammar to create concrete sessions. For POP3, the paper shows this test trace:

```text
Server: +OK Dovecot ready.
Client: USER debug@localdomain.test
Server: +OK
Client: PASS NEWpass123
Server: +OK Logged in.
Client: LIST 8
Server: +OK 8 383
Client: QUIT
Server: +OK Logging out.
```

AutoSpec runs generated sessions against a real server and records parser errors, request-response traces, successes, failures, and timeouts.

## 8. Stage 4: repair the grammar

The Grammar Repair Agent receives the current grammar plus parser and SUT evidence.

1. **Classify:** Choose an error class or `None` and explain briefly.
2. **Localize:** Identify the target nonterminal and concrete failing fragment.
3. **Reduce the diff:** Inline the target rule, reduce actual and expected snippets to terminals, and compute a minimal edit script.
4. **Generate patch:** Rewrite a production, update constraints, or add alternatives using minimal change.
5. **Return structured report:** Emit JSON containing class, target, rationale, and patch entries.

The generator integrates the patch, revalidates the grammar, and reruns MTP tests. Repair stops when schema checks pass and all MTPs are generatable, or when the repair budget is exhausted.

## 10. Implementation and model settings

- Each agent runs in its own sandbox to avoid role cross-talk.
- Outputs use schema-constrained JSON and local Pydantic validation.
- Invalid outputs trigger bounded retries with minimal edits.
- Retrieval and model responses are cached.
- The orchestrator is CPU-only; SUTs run in containers or sockets.
- Default model family: GPT-4-class.
- Fixed decoding: `top_p=1.0`, no stop sequences.
- Temperature is described as `0.1` for generation and `0.0` for lightweight classification; the paper also summarizes the overall fixed setting as temperature zero, so the more specific task-level values should govern reproduction.
- Long grammar generation allows up to 4,000 tokens.
- Tests use at most seven iterations per MTP per protocol.

## 11. Evaluation

### Protocols and implementations

| Protocol | RFC pages | Implementation | Port | Golden grammar LoC | Expert time |
|---|---:|---|---:|---:|---:|
| POP3 | 23 | Dovecot 2.3.19.1 | 110 | 295 | 3.5 h |
| SMTP | 95 | Postfix 3.7.11 | 25 | 373 | 9.5 h |
| IMAP | 108 | Dovecot 2.3.19.1 | 143 | 676 | 14 h |
| FTP | 69 | vsFTPd 1.3.7a | 21 | 576 | 5.5 h |
| ManageSieve | 49 | Pigeonhole 0.5.19 | 4190 | 449 | 5 h |

FTP evaluation covers only the control channel.

### Metrics

- **Element recall:** fraction of golden elements recovered.
- **Element precision:** fraction of generated elements present in the golden grammar.
- **Message acceptance (MA):** fraction of commands receiving positive protocol-conformant responses.
- **Trace acceptance (TA):** fraction of complete sessions accepted and reaching the expected terminal state.
- **RtCMA/RtCTA:** acceptance restricted to actions on golden canonical routes.

```text
Element precision = overlap / generated elements
Element recall    = overlap / golden elements
```

## 12. Results

### RQ1: specification diversity

| Element type | Average recall | Average precision |
|---|---:|---:|
| Client message types | 92.8% | 99.2% |
| Server message types | 80.2% | 94.3% |
| Independent constraints | 16.7% | 42.3% |
| Dependent constraints | 0.0% | 0.0% |

Message formats are recovered well, especially client commands explicitly listed in RFC grammar. Constraint recovery is the main weakness because ranges, cross-field relationships, and temporal rules are dispersed through prose.

### RQ2: execution precision

Message acceptance by protocol:

| POP3 | SMTP | IMAP | FTP | ManageSieve | Average |
|---:|---:|---:|---:|---:|---:|
| 92.9% | 72.7% | 90.0% | 80.6% | 71.4% | 81.5% |

Trace acceptance ranges from 57.1% for SMTP to 90.0% for POP3. Canonical-route acceptance is often higher. Failures include missing implementation features, TLS requirements, missing data/state prerequisites, and grammar bugs.

### RQ3: repair impact

Repair improves server-message recall substantially compared with text-only generation. Most syntax errors are fixed in rounds 2-3. The survival curve then flattens because trace mismatches and semantic coverage errors form a harder tail.

Without repair, examples include POP3 server-message recall at 66.7% instead of 100% and FTP at 26.7% instead of 66.7%.

### RQ4: naive prompting

| Setting without RFC context | Syntactically valid | Executable | Command coverage |
|---|---:|---:|---:|
| Zero-shot schema only | 0/5 | No | 0% |
| Few-shot with two unrelated examples | 2/5 | No | below 10% |
| Command list only | 3/5 | No | about 40% |

None produced an executable grammar. RFC grounding and execution-guided repair are essential.

## 13. Contributions

1. End-to-end conversion of semi-structured natural-language RFCs into executable, session-level formal specifications.
2. Combined modeling of syntax, protocol states, transitions, roles, and semantic constraints.
3. Sentence-level traceability.
4. Automated execution-guided specification repair.
5. Reusable grammars that separate nondeterministic LLM translation from deterministic future testing.

## 14. Limitations

- BM25 retrieval can miss rules split across sections.
- Constraint extraction is weak, especially dependent constraints.
- Repairs may overfit to implementation deviations rather than the RFC.
- Popular-protocol training contamination is possible.
- Evaluation covers five ASCII-oriented session protocols, not binary, encrypted, real-time, or automotive protocols.
- Golden grammars were written by one author, introducing expert-reference dependence.
- The repair loop has a seven-round evaluation cap and no guarantee of complete correctness.
- Some paper cross-references contain drafting artifacts, such as a missing fix-report figure/table reference.

## 15. Reproduction outline

1. Crawl and clean RFC HTML while preserving provenance.
2. Run section filtering and structured extraction with schema validation.
3. Build accepted micrographs and merge them deterministically.
4. Compute minimal transition paths.
5. Retrieve path-relevant RFC clauses.
6. Generate and validate an I/O grammar.
7. Use Fandango to generate tests and execute them against the SUT.
8. Classify failures and create minimal repair patches.
9. Repeat up to the configured budget.
10. Compare grammar elements with the golden grammar and calculate MA/TA.

## 16. Compact mental model

```text
RFC prose
  -> traceable structured protocol facts
  -> minimal valid interaction paths
  -> executable I/O grammar
  -> concrete tests against a real server
  -> failures converted into minimal grammar patches
  -> refined reusable formal specification
```

## 17. Glossary

- **RFC:** Request for Comments, commonly an Internet protocol standard.
- **SUT:** System under test.
- **I/O grammar:** Grammar describing role-tagged, stateful interactions and constraints.
- **MTP:** Minimal transition path to a target behavior.
- **Fandango:** Grammar-based fuzzer used to generate and execute protocol tests.
- **Golden grammar:** Expert-written reference specification.
- **MA/TA:** Message acceptance and trace acceptance.
- **Provenance:** Link from generated artifact to source RFC section and paragraph.
