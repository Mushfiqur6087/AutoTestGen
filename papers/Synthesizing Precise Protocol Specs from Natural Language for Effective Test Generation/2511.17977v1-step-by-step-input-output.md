# AutoSpec: Step-by-Step Input and Output Guide

## Scope and running example

This guide traces [2511.17977v1.pdf](2511.17977v1.pdf) using the paper's POP3 `LIST` example.

- The RFC excerpt, grammar idea, test trace, prompts in Figures 4/6/7, protocol list, and metrics come from the paper.
- Compact JSON and graph records below are pedagogical simplifications of the paper's schemas.
- Prompt panels are formatted transcriptions of visible figure content; the paper does not specify API system/user role boundaries.

### Goal

Convert RFC 1939 prose about POP3 into an executable grammar that generates a session containing:

```text
USER -> PASS -> LIST 8 -> QUIT
```

## Step 1 - Crawl and clean the RFC

### Who performs this step

Deterministic crawler and preprocessing code.

### Input

RFC 1939 HTML, including headings, paragraphs, examples, and boilerplate.

### How this step is done, simply

1. Download/read the RFC HTML.
2. Remove navigation, contents, headers, and footers.
3. Preserve section IDs and paragraph indices.
4. Write one JSON object per section.

### Prompt used

None.

### Output

```json
{
  "rfc_id": "RFC1939",
  "section": "5",
  "paragraphs": [
    {"index": 12, "text": "Once the client has successfully identified itself..."},
    {"index": 13, "text": "The LIST command may be issued in the TRANSACTION state..."}
  ]
}
```

## Step 2 - Classify the RFC section

### Who performs this step

LLM and structured-output parser.

### Input

One cleaned RFC section.

### How this step is done, simply

The LLM determines whether the section contains state-machine rules, an overview, an example, or other content. It chooses `extract`, `copy`, or `summarize`. Only rule-bearing `extract` sections receive detailed processing.

### Prompt used

The paper describes a four-block prompt: Objective, Requirements, Input format, and Output format. It requires a domain-specific RFC role, a four-way schema, a summary no longer than 30 tokens, no extra keys, and provenance. The full prompt is not printed as text.

### Output

```json
{
  "section_id": "5",
  "label": "state machine",
  "action": "extract",
  "summary": "Authorization enters transaction state and enables mailbox commands.",
  "paragraph_indices": [12, 13]
}
```

### Alternate branches

- `copy`: keep exact content as context.
- `summarize`: retain compact context without detailed extraction.
- `other`: omit from rule extraction.

## Step 3 - Extract states, commands, and transitions

### Who performs this step

LLM, response parser, and Pydantic validator.

### Input

The section record whose action is `extract`.

### How this step is done, simply

1. The prompt supplies the section text and metadata.
2. The LLM lifts prose into normalized fields.
3. Missing fields become `null` rather than disappearing.
4. Pydantic checks required fields, types, and allowed values.
5. Invalid output is discarded and prompted once more.

### Prompt used - Figure 4 excerpt

```text
1. Assign Task:
Process the RFC input object shown in 2. RFC Input.
Apply the Guidelines to extract states/commands/transitions/etc.
Return a flat JSON exactly conforming to the Output Schema.

2. RFC Input:
{"section": 3, "paragraph": [...], "type": "overview", "action": "extract"}

3. Guidelines:
Literal: use RFC wording for names/values.
Scope: extract from this section only.
Dependencies: list prerequisites in depends_on.

4. Output Schema:
section, states, commands, transitions, ...
```

The figure contains a fuller JSON schema. This is a readable excerpt, not the entire serialized prompt.

### Output

The paper's Figure 5 shows USER/PASS data. Simplified:

```json
{
  "commands": [
    {
      "name": "USER",
      "allowed_states": ["AUTHORIZATION"],
      "success_transition": null,
      "response_type": "single-line",
      "arguments": [{"name": "username", "regex": "..."}],
      "depends_on": []
    },
    {
      "name": "PASS",
      "allowed_states": ["AUTHORIZATION"],
      "success_transition": {"from": "AUTHORIZATION", "to": "TRANSACTION"},
      "arguments": [{"name": "password", "regex": "..."}],
      "depends_on": ["USER"]
    }
  ]
}
```

## Step 4 - Build a section-local micrograph

### Who performs this step

LLM followed by deterministic acceptance filter.

### Input

Validated section JSON.

### How this step is done, simply

The LLM harmonizes aliases, merges duplicates, and adds implied local edges. The filter then enforces node/edge types and provenance and resolves conflicts in favor of normative text.

### Prompt used

The paper describes this LLM task but does not print its complete prompt.

### Output

```yaml
nodes:
  - AUTHORIZATION: state
  - TRANSACTION: state
  - USER: command
  - PASS: command
edges:
  - AUTHORIZATION invokes USER
  - AUTHORIZATION invokes PASS
  - USER enables PASS
  - PASS yields TRANSACTION
provenance:
  rfc: RFC1939
  section: 5
```

### Failure branch

Reject graph elements with missing provenance, invalid types, or unresolved conflicts.

## Step 5 - Merge all micrographs

### Who performs this step

Deterministic program code.

### Input

All accepted section-local graphs and extracted JSON fragments.

### How this step is done, simply

1. Normalize names such as `User`, `USER`, and `user` to `USER`.
2. Convert dependency edges to `requires` or `enables`.
3. Union nodes and edges while retaining every source anchor.
4. Intersect compatible constraints and flag contradictions.

### Prompt used

None. The paper emphasizes that the global merger is rule-based.

### Output

```text
Protocol multigraph G:
states = {AUTHORIZATION, TRANSACTION, UPDATE}
commands = {USER, PASS, STAT, LIST, DELE, QUIT, ...}
edges = {invokes, yields, requires, enables}
constraints = global constraint store
```

## Step 6 - Compute minimal transition paths

### Who performs this step

Graph-search code.

### Input

Global protocol multigraph plus initial state.

### How this step is done, simply

For each target command, search for the shortest edge sequence that satisfies all prerequisites and preconditions and establishes the desired destination state.

### Prompt used

None.

### Output

For target `LIST` followed by shutdown:

```text
AUTHORIZATION --USER--> AUTHORIZATION
AUTHORIZATION --PASS--> TRANSACTION
TRANSACTION   --LIST--> TRANSACTION
TRANSACTION   --QUIT--> UPDATE
```

This MTP also points to the exact RFC paragraphs needed for grammar generation.

## Step 7 - Retrieve path-relevant RFC evidence

### Who performs this step

BM25 retriever and program code.

### Input

The MTP and structured RFC content index.

### How this step is done, simply

Use states, commands, and edges from the path as retrieval keys. Return the smallest set of normative clauses, syntax listings, and constraints needed to describe the interaction.

### Prompt used

None for retrieval.

### Output

```yaml
minimal_path: AUTHORIZATION USER PASS TRANSACTION LIST QUIT UPDATE
retrieved_rfc_text:
  - USER syntax and response clauses
  - PASS transition clause
  - LIST syntax, state restriction, and response clauses
  - QUIT transition clause
```

## Step 8 - Generate the initial I/O grammar

### Who performs this step

Grammar Generator LLM plus parser/Pydantic guardrails.

### Input

Minimal transition path, retrieved RFC evidence, target grammar scaffold, and generation rules.

### How this step is done, simply

1. Convert the MTP into an FSM/exchange skeleton.
2. Fill productions from RFC evidence.
3. Add `where` constraints.
4. Create `<start>` and `<terminals>`.
5. Deduplicate and normalize symbols.
6. Return grammar only.

### Prompt used - Figure 6 excerpt

```text
1. Assign Task:
From a Minimal Path and Retrieved Protocol Info, synthesize a complete
Fandango grammar. Use the rules below and output raw grammar only.

2. Inputs:
Minimal Transition Path: AUTHORIZATION (APOP) + TRANSACTION (LIST QUIT)
Retrieved RFC text: { ... }

3. Rules:
Prefixes: on RHS only, <Client:...>, <Server:...>
Notation: <non-terminal> ::= ... | ...
Order: states -> exchanges -> client commands -> server responses
Terminals include <space>, <crlf>, <text>, <number>, etc.

4. Guidelines:
Parse the minimal path, extract syntax/constraints only from retrieved
context, build grammar, and enforce response rules.

5. Output: I/O Grammar
```

### Output

A grammar containing exchanges such as:

```text
<transaction_exchanges> ::= <Client:LIST> <Server:list_response>
<Client:LIST> ::= "LIST" <space> <message_number> <crlf>
<message_number> where 1 <= int(<message_number>) <= 8
```

The notation is simplified from Figure 1 for readability.

### Failure branch

If schema/model or MTP-generatability checks fail, reject the output and reissue the prompt once.

## Step 9 - Generate a concrete protocol test

### Who performs this step

Fandango grammar-based fuzzer.

### Input

Executable I/O grammar and selected MTP.

### How this step is done, simply

Fandango expands grammar productions while satisfying constraints, producing concrete client and expected server messages.

### Prompt used

None. Test generation is grammar-driven and reproducible.

### Output

The paper's POP3 example:

```text
connect
Server: +OK Dovecot ready.
Client: USER debug@localdomain.test
Server: +OK
Client: PASS NEWpass123
Server: +OK Logged in.
Client: LIST 8
Server: +OK 8 383
Client: QUIT
Server: +OK Logging out.
```

## Step 10 - Execute against the system under test

### Who performs this step

Fandango runner, socket/container infrastructure, and the real protocol implementation.

### Input

Concrete message session and expected response grammar.

### How this step is done, simply

Send each client command, collect the server response, parse it against the grammar, track state, and save successes, rejections, timeouts, and parser errors.

### Output

```yaml
request: "LIST 8\r\n"
response: "+OK 8 383\r\n"
accepted: true
state_after: TRANSACTION
```

### Failure branch

A failure may be caused by grammar syntax, trace mismatch, coverage omission, missing SUT feature, TLS prerequisite, or missing data/state.

## Step 11 - Classify and localize a grammar failure

### Who performs this step

Grammar Repair LLM.

### Input

Current grammar, Fandango/parser error, request-response trace, and RFC context.

### How this step is done, simply

1. Classify the error.
2. Identify the failing nonterminal.
3. Capture the concrete input fragment.
4. Inline the rule and compare actual versus expected terminal sequences.
5. Compute the smallest difference.

### Prompt used - Figure 7 excerpt

```text
1. Assign Task:
Using Current Grammar and FANDANGO Error, apply Global Rules and the
Workflow to diagnose the issue and propose the minimal correction(s).
Return one JSON fix report that matches the Output Schema exactly.

2. Inputs:
Current Grammar
FANDANGO Error
RFC Context

3. Rules:
Prefixes on RHS only; preserve notation, order, and terminals.

4. Guidelines:
Classify, locate the target rule, reduce terminal sequences, and make a
minimal fix. Replace the target rule with the smallest corrected production.

5. Output:
error_class, target_rule, reason, offending_line, patch, updated syntax
```

### Output

```json
{
  "error_class": "Trace Mis-match",
  "target_rule": "Server:list_response",
  "reason": "Observed response alternative is absent.",
  "patch": ["add the RFC-supported response alternative"],
  "provenance": "RFC1939 section/paragraph anchor"
}
```

This example report is reconstructed; the field categories follow Figure 7.

## Step 12 - Apply the minimal patch

### Who performs this step

Grammar Generator LLM plus deterministic normalization and validation code.

### Input

Current grammar, structured fix report, MTP, and RFC evidence.

### How this step is done, simply

The generator edits only the targeted production or constraint, preserves canonical names and provenance, then reruns deduplication, terminal completeness, schema checks, and MTP generatability.

### Prompt used

The generator prompt from Figure 6 is reused with fixer guidance. The complete patch-integration message is not separately printed.

### Output

Revised executable grammar with a minimal diff.

## Step 13 - Repeat execution and repair

### Who performs this step

Orchestrator, Fandango, SUT, Repair Agent, and Generator Agent.

### Input

Revised grammar.

### How this step is done, simply

Regenerate the MTP tests, execute them, and send remaining failures back into Steps 11-12. Evaluation allows up to seven iterations per MTP.

### Output

Either another repair report or a grammar whose schema checks and MTP generation succeed.

### Terminal branches

- **Success:** return refined grammar.
- **Budget exhausted:** stop with remaining unresolved problems.

## Step 14 - Use the final grammar for testing

### Who performs this step

Fandango and test infrastructure; no LLM is required.

### Input

Refined grammar and a client or server implementation.

### How this step is done, simply

Generate many valid stateful sessions and use the grammar as both input generator and response oracle.

### Output

- Test sessions.
- Message acceptance results.
- Trace acceptance results.
- Rejections and conformance failures.

## Component contract table

| Component | Actor | Input | Transformation | Output |
|---|---|---|---|---|
| RFC crawler | Code | RFC HTML | Clean and split | Section JSON |
| Section filter | LLM | Section | Label and route | Action record |
| Structured extractor | LLM + Pydantic | Extract section | Lift protocol facts | Validated JSON |
| Micrograph synthesizer | LLM + filter | JSON fragment | Harmonize and connect | Accepted local graph |
| Global merger | Code | Local graphs | Normalize and union | Protocol multigraph |
| MTP finder | Graph algorithm | Multigraph | Shortest valid paths | MTPs |
| Retriever | BM25 | MTP + RFC index | Select clauses | RFC evidence |
| Grammar generator | LLM + validators | MTP + evidence | Synthesize grammar | Initial/revised grammar |
| Test generator | Fandango | Grammar | Expand productions | Concrete sessions |
| SUT runner | Code + implementation | Session | Exchange messages | Trace/errors |
| Repair agent | LLM | Grammar + errors + RFC | Diagnose minimal delta | JSON fix report |
| Patch integration | LLM + code | Fix report + grammar | Minimal edit and normalize | Refined grammar |

## Final mental model

```text
RFC facts are extracted with provenance
    -> deterministic graph captures valid behavior
    -> shortest paths focus retrieval
    -> LLM writes an executable grammar
    -> fuzzer tests a real implementation
    -> failures become minimal grammar patches
    -> final grammar generates future tests without an LLM
```
