# WebTestPilot: Step-by-Step Input and Output Guide

## Scope and evidence labels

This guide traces [2602.11724v3.pdf](2602.11724v3.pdf) through the paper's Amazon camera-shopping example.

- The six GUI states, `Product`/`Cart` schemas, symbol extraction pattern, subtotal checks, DSL, and architecture come from the paper.
- Compact JSON responses and prompt templates below are pedagogical reconstructions unless explicitly described otherwise.
- The PDF describes prompt tasks but does not print complete prompt text or API system/user roles.

## Running requirement

```text
Starting from an empty cart, continue shopping. Search for "camera" and verify
that suggestions appear. Open the first search result and add the product to
the cart. Verify that the selected product is present with the correct price
and quantity and that the cart subtotal increases correctly.
```

This wording condenses the exact flow and assertions depicted in Figures 2-6; it is not quoted as one paper-provided requirement.

## Step 1 - Parse the natural-language description

### Who performs this step

LLM plus JSON parser.

### Input

The running requirement as raw text.

### How this step is done, simply

1. Send the raw text to an LLM.
2. Ask it to preserve order and divide the text into disjoint steps.
3. Require every step to contain a condition, action, and expectation.
4. Optionally infer missing steps.
5. Parse the returned JSON.

### Prompt used

The paper does not print it. Illustrative reconstruction:

```text
Convert the test description into an ordered JSON list of test steps.
For each step return condition, action, and expectation. Preserve source order,
do not duplicate text across steps, and infer missing operational steps only
when configured.
```

### Output

```yaml
- condition: Cart page is open and empty.
  action: Click Continue Shopping.
  expectation: Home page is displayed.
- condition: Search bar is visible.
  action: Type camera.
  expectation: Search suggestions appear and the search value is camera.
- condition: Search results are displayed.
  action: Open the first product.
  expectation: Product details match the first result.
- condition: Product detail page is open.
  action: Click Add to Cart.
  expectation: Cart contains the product with correct quantity, price, and subtotal.
```

## Step 2 - Initialize session state

### Who performs this step

Browser automator and program code.

### Input

Starting URL and first structured step.

### How this step is done, simply

Open the application, capture a full screenshot and DOM, flatten DOM elements, assign a state object, and create an empty chronological session history.

### Prompt used

None.

### Output

```yaml
session:
  history: []
  state:
    screenshot: cart_empty.png
    dom: DOM_tree
    page_id: pending
```

## Step 3 - Assign or reuse a page identifier

### Who performs this step

DOM tree-distance code plus LLM visual comparison.

### Input

New state and prior session states.

### How this step is done, simply

1. Find the prior DOM with smallest tree-edit distance.
2. If no candidate exists, assign a new ID.
3. Otherwise give current and candidate screenshots to an LLM.
4. Ask whether they represent the same logical page.
5. Reuse or create `page_id`.
6. Store a textual `(page_id, summary, layout)` record.

### Prompt used

The complete prompt is not printed. Illustrative reconstruction:

```text
Compare these two screenshots. Do they represent the same logical application
page despite changed data or layout details? Return same_page and a concise
page summary.
```

### Output

```yaml
page_id: cart
summary: Cart page with no current items.
layout: Header, empty-cart message, Continue Shopping link.
```

## Step 4 - Infer explicit and implicit requirements

### Who performs this step

LLM.

### Input

Current step's condition/expectation and textual session trace.

### How this step is done, simply

The model asks what must be true beyond the literal words and identifies:

- causal effects of the action;
- values that must propagate between pages;
- earlier visits to the same page that must be compared.

### Prompt used

Not printed. Illustrative reconstruction:

```text
Given the explicit condition, expectation, and session trace, infer all testable
causal, data, and temporal dependencies needed for a reliable oracle. Do not
invent behavior unrelated to the requirement.
```

### Output for Add to Cart

```yaml
explicit:
  - selected product appears in cart
implicit:
  - prior cart items remain
  - exactly one matching product is added
  - title and price match the viewed product
  - quantity is one
  - subtotal equals prior subtotal plus added price times quantity
  - compare current cart with the earlier state whose page_id is cart
```

## Step 5 - Define relevant custom schemas

### Who performs this step

LLM generating Pydantic code, followed by schema validation/runtime.

### Input

Explicit/implicit requirements and relevant state summaries.

### How this step is done, simply

Create the smallest typed symbols needed for the assertions. Fields receive type, required/optional, and range constraints.

### Prompt used

Not printed. The paper states that custom symbols are defined in Pydantic. Illustrative reconstruction:

```text
Define only the Pydantic symbol schemas needed to verify the requirements.
Use typed fields and domain constraints. Do not instantiate values yet.
```

### Output from the paper's example

```python
class Product(BaseModel):
    title: str = Field(...)
    price: float = Field(..., ge=0)
    quantity: Optional[int] = Field(None, gt=0)

class Cart(BaseModel):
    items: List[Product] = Field(...)
```

## Step 6 - Generate DSL precondition and postcondition

### Who performs this step

LLM constrained to the Python-extended DSL.

### Input

Schemas, explicit/implicit requirements, and available built-in symbols/methods.

### How this step is done, simply

The LLM writes executable predicates using only declared custom symbols, `Session`, `State`, `Element`, their methods, Python comparisons, and supported standard-library operations.

### Prompt used

The PDF prints the DSL grammar but not the prompt. Illustrative reconstruction:

```text
Write executable precondition and postcondition assertions using only the
provided schemas and DSL. Extract symbol values from appropriate current or
historical states. Cover every explicit and inferred requirement.
```

### Output

```python
added = session.history[-1].extract("Get product detail", schema=Product)
current = session.state.extract("Get cart summary", schema=Cart).items
prior = session.history[-2].extract("Get cart summary", schema=Cart).items

for prod in prior + [added]:
    match = next((p for p in current if p.title == prod.title), None)
    assert match is not None
    assert match.quantity == prod.quantity
    assert match.price == prod.price

prior_subtotal = sum(p.price * p.quantity for p in prior)
added_total = added.price * added.quantity
current_subtotal = sum(p.price * p.quantity for p in current)
assert current_subtotal == prior_subtotal + added_total
```

## Step 7 - Evaluate the precondition

### Who performs this step

DSL runtime, state extractor, VLM/LLM perception, and Pydantic validation.

### Input

Current state plus `PreconditionDSL`.

### How this step is done, simply

Resolve `find()` and `extract()` calls against screenshot/DOM data, instantiate requested schemas, then execute the assertions.

### Output

```yaml
precondition_passed: true
```

### Failure branch

Regenerate the assertion and retry once (`n=1`). Persistent failure becomes an inconsistency/bug report without executing an invalid next action.

## Step 8 - Predict a coarse action location

### Who performs this step

UI-Venus-7B GUI grounding model.

### Input

Full screenshot and natural-language action, such as `Click Add to Cart`.

### How this step is done, simply

The grounding model predicts approximate screen coordinates. This fast stage narrows the search region but does not directly execute the click.

### Prompt used

Model-specific grounding input; no full prompt is printed.

### Output

```yaml
coarse_target:
  x: 812
  y: 641
```

Coordinates are illustrative.

## Step 9 - Refine into a precise executable action

### Who performs this step

Set-of-Mark annotator plus LLM.

### Input

Action text, cropped screenshot around the coarse target, and IDs/bounds for interactable elements.

### How this step is done, simply

1. Annotate interactable elements from the UI tree.
2. Crop a square around the coarse prediction.
3. Ask the LLM to select action type, element ID, and parameter.

### Prompt used

Not printed. The action type must be one of `click`, `type`, `press`, `scroll`, or `wait`.

### Output

```yaml
action:
  type: click
  element_id: mark_17
  parameters: null
```

## Step 10 - Execute action and capture successor state

### Who performs this step

Browser automator and web application.

### Input

Precise action.

### How this step is done, simply

Execute the interaction, wait for UI stabilization, then capture the new screenshot and DOM.

### Prompt used

None.

### Output

```yaml
new_state:
  screenshot: cart_with_camera.png
  dom: updated_DOM
```

## Step 11 - Reidentify and store the successor state

### Who performs this step

The page-reidentification pipeline from Step 3.

### Input

New cart state and session history containing the earlier empty-cart state.

### How this step is done, simply

The DOM filter selects the earlier cart as nearest, and the LLM confirms both screenshots represent the Cart page. The new state reuses `page_id=cart` and enters history.

### Output

```yaml
page_id: cart
session_history_appended: true
```

This link enables temporal comparison of cart contents before and after shopping.

## Step 12 - Extract symbol values on demand

### Who performs this step

State extraction model/runtime and Pydantic.

### Input

Current and historical states plus extraction instruction and schema.

### How this step is done, simply

Extract only values referenced by the assertion. Parse them into typed schema instances and reject invalid values.

### Output

```yaml
added:
  title: 4K Digital Camera for Photography
  price: 82.99
  quantity: 1
prior_cart:
  items: []
current_cart:
  items:
    - title: 4K Digital Camera for Photography
      price: 82.99
      quantity: 1
  subtotal: 82.99
```

## Step 13 - Execute the postcondition oracle

### Who performs this step

Python/DSL runtime.

### Input

Instantiated symbols and `PostconditionDSL`.

### How this step is done, simply

Run every assertion. The program checks membership, value equality, quantity, and subtotal arithmetic without asking the LLM to make a final free-form judgment.

### Output: passing state

```yaml
postcondition_passed: true
step_status: success
```

### Output: bug state

```yaml
postcondition_passed: false
failed_assertion: current_subtotal == prior_subtotal + added_total
observed: 72.99
expected: 82.99
```

## Step 14 - Retry or report inconsistency

### Who performs this step

Controller code and, for regeneration, the LLM assertion generator.

### Input

Failed predicate, state trace, symbols, and retry count.

### How this step is done, simply

If budget remains, regenerate the assertion and execute again to reduce hallucination risk. The reported evaluation uses one retry. If the failure persists, classify it as an inconsistency/bug.

### Prompt used

The retry prompt is not printed. Illustrative reconstruction:

```text
The predicate failed on the supplied states. Recheck the requirement,
dependencies, declared symbols, and DSL validity. Produce a corrected predicate
only if the previous assertion was wrong; otherwise preserve the assertion.
```

### Output

```yaml
report_type: inconsistency
step: Add product to cart
evidence: Cart subtotal does not equal prior subtotal plus added item total.
```

## Step 15 - Continue or terminate the test

### Who performs this step

Controller code.

### Input

Current step result and remaining structured steps.

### How this step is done, simply

- If the step succeeds, advance to the next step.
- If a persistent predicate fails, stop/report a bug.
- If every step succeeds, mark the entire test complete.

### Output

```yaml
task_completion: 1
correct_trace: 1.0
bug_reports: []
```

## Terminal paths

### Successful flow

All preconditions, actions, and postconditions succeed -> complete trace.

### Real application bug

Valid assertion repeatedly fails on the bug-injected state -> true-positive report.

### Assertion hallucination

Incorrect generated assertion fails on a correct state -> regenerate/retry; if unresolved, false positive.

### Action failure

Grounding/execution reaches wrong state -> ground-truth test-script assertion reduces TC/CT during evaluation; runtime handling follows step control.

### Incomplete/ambiguous requirement

Parser omits or invents steps -> downstream errors. The paper recommends proactive semantic parsing, clarification, and external-context retrieval.

## Component contract table

| Component | Actor | Input | Transformation | Output |
|---|---|---|---|---|
| Input parser | LLM + parser | Raw requirement | Split and structure | NL step tuples |
| Page reidentifier | DOM distance + LLM | New/prior states | Match logical page | Page ID + summary |
| Dependency inference | LLM | Step + trace | Infer implicit expectations | Dependency list |
| Schema generator | LLM + Pydantic | Expectations | Define symbols | Typed schemas |
| DSL generator | LLM | Symbols + requirements | Compose predicates | Pre/postconditions |
| Symbol extractor | Perception + Pydantic | State + schema | Read/validate GUI data | Symbol values |
| Precondition runner | Python DSL | State + predicate | Execute assertion | Pass/fail |
| Coarse grounding | UI-Venus-7B | Full screenshot + action | Predict region | Coordinates |
| Precise action selector | SoM + LLM | Crop + marked elements | Select operation | Executable action |
| Browser automator | Code | Action | Interact and capture | Successor state |
| Postcondition runner | Python DSL | States/symbols + predicate | Execute oracle | Pass/fail/evidence |
| Retry controller | Code + LLM | Failed assertion | Regenerate/re-execute | New verdict/report |

## Final mental model

```text
LLM understands what should be checked.
Symbols represent what the GUI contains.
Python assertions decide whether it is correct.
Grounded actions move the application forward.
Page IDs connect the past with the present.
```
