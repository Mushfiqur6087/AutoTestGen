# Learning Guide: WebTestPilot

## Paper at a glance

- **Title:** *WebTestPilot: Agentic End-to-End Web Testing against Natural Language Specification by Inferring Oracles with Symbolized GUI Elements*
- **Authors:** Xiwen Teoh, Yun Lin, Duc-Minh Nguyen, Ruofei Ren, Wenjie Zhang, and Jin Song Dong
- **Publication:** Proceedings of the ACM on Software Engineering, FSE 2026; arXiv:2602.11724v3, 23 April 2026
- **Source:** [2602.11724v3.pdf](2602.11724v3.pdf)
- **Goal:** Convert arbitrary natural-language web test requirements into executable end-to-end actions and reliable pre/postcondition oracles.
- **Core idea:** Use VLM/LLM perception to extract structured GUI symbols, then generate bounded Python-like assertions over those symbols rather than trusting free-form model judgments.
- **Main benchmark result:** 99% task completion and 96% precision/recall for bug detection.

WebTestPilot does not train a new foundation model. It orchestrates existing LLM/VLM and grounding models at inference time with symbolic schemas, a DSL, retries, and page history.

## 1. Problem

Reaching the end of a GUI flow does not prove that the application behaved correctly. A useful E2E test needs an oracle that decides whether every observed state agrees with the requirement.

LLM agents face two problems:

1. **Oracle capability:** They must infer implicit expectations and data, causal, and temporal dependencies that are not stated as simple final-screen checks.
2. **Oracle reliability:** Free-form stochastic reasoning changes across trials, producing flaky verdicts.

In the paper's preliminary study, five LLM families answer the same "does the cart contain only one item?" question ten times each and produce seven distinct reasons. If every step has independent correctness probability `p`, an `n`-step trajectory succeeds with probability roughly `p^n`, so small step errors compound.

## 2. Why symbolization helps

WebTestPilot constrains reasoning to declared symbols such as `Product`, `Cart`, `State`, and `Session`.

- **Reliability:** Assertions come from a discrete, explicit vocabulary rather than unbounded natural-language judgment.
- **Accuracy:** Symbols expose data and relationships across states.
- **Recoverability:** Values can be extracted on demand from retained states rather than preselected before their future relevance is known.
- **Scalability:** Page reidentification finds relevant prior states instead of symbolizing every visible element eagerly.

## 3. Formal problem

A web state contains:

```text
state = screenshot + DOM tree
```

An action contains:

```text
action = action type + target element + optional parameter
```

A natural-language document is divided into ordered, disjoint, semantically complete steps. Each step produces:

```text
precondition predicate + executable action + postcondition predicate
```

A predicate maps a state to true or false. A test passes only if every precondition holds, every action executes, and every postcondition holds.

## 4. Inputs, intermediate artifacts, and outputs

### External inputs

- Natural-language test requirement from PRD, user story, email, chat, technical design, or documentation.
- Running web application.
- Screenshot and DOM for each current state.
- Optional configuration for filling missing steps, model selection, and retries.

### Intermediate artifacts

- Ordered `(conditionNL, actionNL, expectationNL)` steps.
- Execution trace and session history.
- Page identifiers connecting logically equivalent pages.
- State summaries/layouts.
- Explicit and inferred implicit requirements.
- Custom Pydantic schemas.
- Instantiated symbols extracted from GUI states.
- Python-extended DSL precondition and postcondition assertions.
- Coarse target coordinates, marked/cropped screenshots, and executable actions.

### Final outputs

- Completed execution trace.
- Pass/fail for each assertion and test step.
- Inconsistency/bug report after persistent assertion failure.
- In experiments: task-completion, correct-trace, precision, and recall measurements.

## 5. Architecture

```text
Natural-language test description
  -> Input Parsing
      ordered condition/action/expectation steps
  -> for each step:
      Oracle Inference
        infer dependencies
        reidentify pages
        define/extract symbols
        generate DSL pre/postconditions
      Oracle Execution
        evaluate precondition
        generate and execute action
        capture/reidentify new state
        evaluate postcondition
        retry failed assertion
  -> inconsistency report or successful trace
```

## 6. Input parsing

An LLM receives the raw requirement and returns JSON containing steps. The parser may infer missing steps if configured.

Each step must preserve:

- **Disjointness:** no source token contributes to multiple steps.
- **Monotonicity:** step order follows source order.
- **Semantic completeness:** condition, action, and expectation are represented.

The paper does not print the complete parsing prompt or API role messages.

## 7. Oracle inference

Oracle inference uses two LLM stages for each step.

### Stage 1: infer implicit requirements

The LLM receives the explicit condition/expectation plus a textual execution trace. It identifies:

- **Causal dependency:** the action in one state directly creates, updates, or deletes something in the next.
- **Data dependency:** a value extracted earlier propagates to a later state.
- **Temporal dependency:** a later visit to the same logical page must be compared with an earlier visit.

### Stage 2: symbolize and write assertions

The LLM defines only relevant Pydantic schemas, extracts values from states, and writes pre/postcondition assertions in the DSL. Actual values are instantiated at runtime.

## 8. Symbols and DSL

### Custom symbols

The paper's shopping example defines:

```python
class Product(BaseModel):
    title: str
    price: float = Field(..., ge=0)
    quantity: Optional[int] = Field(None, gt=0)

class Cart(BaseModel):
    items: List[Product]
```

Schemas validate types, required fields, and domain constraints.

### Built-in symbols

- `Session.history`: chronological states.
- `Session.state`: current state.
- `State.page_id`: logical page identity.
- `State.elements`: flattened UI elements.
- `State.find(description, top_k)`: matching elements.
- `State.extract(instruction, schema)`: schema-conforming data.
- `Element`: bounding box, parent, children, extraction.

### DSL

The DSL extends Python with top-level `assert` statements, Boolean operators, comparisons, values, variables, attributes, and methods. It supports standard functions, regex, functional utilities, conditionals, and loops.

Assertion categories:

1. Existence
2. Relational/spatial/structural
3. Temporal
4. Causal
5. Data integrity

## 9. Oracle execution

For each step:

1. Evaluate `PreconditionDSL` on the current state.
2. Convert `ActionNL` to an executable GUI action.
3. Execute it and capture the successor state.
4. Reidentify the new page and append it to session history.
5. Evaluate `PostconditionDSL`.

If an assertion fails, WebTestPilot can regenerate and retry up to `n` times or generate candidates and vote. The paper uses `n=1`.

## 10. Two-stage action grounding

Pure set-of-mark prompting is stable but costly/noisy. Pure grounding is fast but unstable on unseen sites. WebTestPilot combines them:

1. UI-Venus-7B predicts coarse `(x, y)` target coordinates from the full screenshot and action text.
2. The UI tree supplies marked interactable elements.
3. A square crop around `(x, y)` narrows the region.
4. An LLM maps the crop and natural-language action to:

```text
action type in {click, type, press, scroll, wait}
target element ID
optional parameters
```

## 11. Page reidentification

When a new state arrives:

1. Find the historical state with smallest DOM tree-edit distance.
2. Give both screenshots to an LLM.
3. Ask whether they are the same logical page.
4. Reuse the old `page_id` or assign a new one.
5. Store `(page_id, summary, layout)` and append the state.

This enables comparisons such as cart before shopping versus cart after adding a product.

## 12. Worked Amazon example

The paper's flow:

1. Start at an empty cart.
2. Continue shopping.
3. Type `camera`, causing suggestions.
4. Submit search and view results.
5. Open the first product.
6. Add it to the cart.

### Causal assertions

Compare search-bar state before and after typing:

```python
assert before.dropdown is False and after.dropdown is True
assert before.value is None and after.value is not None
assert after.value == "camera"
```

### Data assertions

Extract search results, selected product, and cart. Verify the selected product flows from results to details to cart.

### Temporal assertions

Compare the earlier and later states that share the Cart page ID. Verify the prior items remain and exactly one matching product is added.

### Subtotal assertion

```python
prior_subtotal = sum(p.price * p.quantity for p in prior)
added_total = added.price * added.quantity
current_subtotal = sum(p.price * p.quantity for p in current)
assert current_subtotal == prior_subtotal + added_total
```

This detects missing/duplicate items, wrong price or quantity, and bad subtotal even when the explicit statement only says that the product is now in the cart.

## 14. Benchmark

### Applications

| App | Test cases | Lines of code |
|---|---:|---:|
| BookStack | 27 | 214,819 |
| Indico | 25 | 573,316 |
| InvoiceNinja | 25 | 1,513,289 |
| PrestaShop | 23 | 2,234,514 |

Selection requires at least 5,000 GitHub stars, over 50 contributors, over 1,000 commits, recent activity, at least five years of availability, practical relevance, and user documentation.

The authors create 100 requirements and corresponding Playwright scripts. Each sample is:

```text
web application + natural-language requirement + assertion script + injected bug
```

### Injected bugs

One bug per requirement, based on thematic analysis of sampled closed GitHub issues:

- missing UI elements;
- data inconsistency;
- no-op actions;
- navigation failures.

Crash-only and cosmetic bugs are excluded.

## 15. Metrics

### Task Completion

`1` only when every state in the trace passes its corresponding ground-truth assertion; otherwise `0`.

### Correct Trace

The fraction of the expected script completed correctly before the first failure.

### Bug detection

```text
Precision = true bug reports / all bug reports
Recall    = detected injected bugs / all injected bugs
```

All generated assertions are manually checked for semantic correctness to rule out coincidental true positives.

## 16. Results

### RQ1: flow completion

| Approach | Total TC | Total CT |
|---|---:|---:|
| LaVague | 0.64 | 0.77 |
| NaviQAte | 0.54 | 0.70 |
| PinATA | 0.08 | 0.18 |
| WebTestPilot | **0.99** | **0.99** |

Median per-step runtime is 29 seconds and median usage is 10k tokens. Page reidentification is the primary bottleneck. WebTestPilot preserves actions through UI changes in 39/40 cases versus XPath 32/40, CSS 33/40, and Playwright 29/40.

### RQ2: bug detection

| Approach | Precision | Recall |
|---|---:|---:|
| PinATA | 0.26 | 0.69 |
| WebTestPilot | **0.96** | **0.96** |

WebTestPilot detects 22 of 23 replicated real GitHub bugs; PinATA detects 15.

### RQ3: robustness to requirement transformation

Inputs are modified with sentence dropout, noise/typos, summarization, and restyling. No transformation is worst for every model. Qwen2.5-VL-72B achieves total TC 0.85 and CT 0.90; GPT-4.1 achieves TC 0.81 and CT 0.86. Performance falls sharply around 7B and below, especially under noise and summarization.

### RQ4: model comparison and assertion quality

With GPT-4.1:

- 91% of predicates reference both prior and current states.
- 41.3% of symbols model physical concepts and 58.7% UI components.
- 78% use membership, 14% `is None`, 18% list length, and 51% relational comparisons.

Local-model assertion errors are 52% incorrect symbol declaration/use, 39% incorrect DSL usage, and 9% runtime type/operation errors.

## 17. Industrial case study

China Mobile applies WebTestPilot to an in-progress warehouse-management application built on a no-code platform.

- PRD preprocessing: 56 test inputs in 6.4 minutes.
- Execution: 32.7 minutes.
- Bugs: eight total - five data-binding, two UI, one navigation.
- Mean time to detect: 4.9 minutes.
- Defect density: 0.14 bugs/page.

The data-related findings include empty required table fields, dropdowns inconsistent with stored warehouses, unbound storage-area options, and an empty supplier list.

## 18. Contributions

1. Neurosymbolic GUI testing using neural symbol extraction plus symbolic assertions.
2. On-demand structured state history with page reidentification.
3. Python-based DSL that captures implicit dependencies.
4. Hybrid grounding plus set-of-mark action execution.
5. Public four-app, 100-bug benchmark.
6. Industry deployment and real bug findings.

## 19. Limitations and threats

- Requirements are assumed self-contained, complete, and ordered.
- Alternative valid GUI paths may cause metric underestimation.
- The benchmark may not represent all real applications or bugs.
- The approach depends on LLM/VLM perception and schema/DSL correctness.
- Page reidentification is expensive.
- Generated actions can become stale, though caching and change detection help.
- `n=1` gives limited retry evidence in the reported experiments.
- The benchmark excludes crashes and purely cosmetic faults.
- Smaller local models frequently misuse schemas and the DSL.
- The main paper does not print full prompts.

## 20. Reproduction outline

1. Deploy the four version-locked Docker Compose applications.
2. Load 100 requirements, Playwright scripts, and injected bugs.
3. Parse each requirement into condition/action/expectation steps.
4. Capture screenshot and DOM states.
5. Maintain page IDs and textual session history.
6. Infer implicit requirements and relevant schemas.
7. Generate and execute DSL predicates.
8. Ground and execute actions with UI-Venus plus marked crops.
9. Retry failed assertions once and report persistent inconsistency.
10. Calculate TC, CT, precision, recall, runtime, and token usage.

## 21. Compact mental model

```text
Natural-language flow
  -> structured test steps
  -> symbols extracted from related GUI states
  -> executable assertions over those symbols
  -> grounded action
  -> new state and page identity
  -> assertion verdict
  -> retry or bug report
```

## 22. Glossary

- **E2E:** End-to-end testing through the user interface.
- **Oracle:** Mechanism deciding whether observed behavior is correct.
- **Symbolization:** Converting GUI content into typed named objects.
- **DSL:** Domain-specific language for assertions.
- **Page reidentification:** Assigning the same ID to repeated visits to one logical page.
- **Set-of-Mark:** Screenshot annotation with element IDs/bounds.
- **TC/CT:** Task Completion and Correct Trace.
