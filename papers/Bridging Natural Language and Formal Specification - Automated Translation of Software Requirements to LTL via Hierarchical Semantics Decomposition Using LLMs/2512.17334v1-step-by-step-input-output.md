# Req2LTL: Step-by-Step Input and Output Guide

## Scope and evidence labels

This guide follows [2512.17334v1.pdf](2512.17334v1.pdf) using the paper's Req03 example from Figure 3.

- The requirement, six decomposition stages, visual tree, and final formula are paper-provided.
- Compact JSON schemas and individual intermediate records are pedagogical representations of the depicted process.
- The paper prints the direct baseline prompt but only describes the Req2OnionL prompt design. Reconstructed prompts are labeled.

## Running input

```text
If the system is in the dual inertial navigation calculation angle working
mode, then globally, the input angle is equal to 0.5 times the product of
the sum of the angles in inertial navigation module 1 and inertial navigation
module 2, and the reasonable flags of both inertial navigation modules is true.
```

| LLM step | Paper evidence | Complete prompt printed? |

## Step 1 - Supply the natural-language requirement

### Who performs this step

Human engineer or batch-processing code.

### Input

Req03 above.

### How this step is done, simply

The requirement is submitted as a text string to Req2OnionL with the OnionL definition, decomposition instructions, grammar constraints, and few-shot demonstrations.

### Prompt used

The complete Req2OnionL prompt is not printed. Illustrative reconstruction:

```text
Using the OnionL definition and BUILDING-ONIONL procedure, decompose the
requirement in two stages. First identify the global scope. Then recursively
extract unary scopes, binary relations, and normalized atomic propositions.
Return grammar-valid OnionL JSON only.

Requirement: {requirement}
```

### Output

An LLM task containing the raw requirement and formal guidance.

## Step 2 - Identify global scope and separate the clause

### Who performs this step

LLM guided by BUILDING-ONIONL Step 1.

### Input

The complete Req03 sentence.

### How this step is done, simply

The model detects a mode-triggered conditional: "if the system is in ... working mode." It separates that mode condition from the behavior after "then."

### Prompt used

Part of the unpublished BUILDING-ONIONL prompt.

### Output

```yaml
scope_type: mode
mode_clause: system is in dual inertial navigation calculation angle mode
main_clause: globally, input angle equals the weighted angle expression and both reasonable flags are true
```

## Step 3 - Construct the top-level OnionL tree

### Who performs this step

LLM guided by BUILDING-ONIONL Step 2.

### Input

Mode clause plus remaining behavior.

### How this step is done, simply

A mode scope is interpreted as an implication antecedent. BUILDING-ONIONL wraps the entire requirement in Globally and places the mode on the left side of Implies.

### Output

```text
Globally(
  Implies(
    mode condition,
    remaining behavior
  )
)
```

### Alternate branch

- Explicit temporal scope: make it the root.
- No scope: wrap the clause in Globally by default.
- Atomic child: normalize directly and terminate.

## Step 4 - Extract nested unary scope

### Who performs this step

LLM guided by BUILDING-ONIONL Step 3.

### Input

The consequent beginning with "globally."

### How this step is done, simply

The model recognizes Globally as a unary temporal operator and creates another `G` node around the remaining consequent.

### Output

```text
G(
  Implies(
    mode condition,
    G(remaining consequent)
  )
)
```

## Step 5 - Split binary logical relations

### Who performs this step

LLM guided by BUILDING-ONIONL Step 4.

### Input

```text
input angle equals the weighted expression,
AND reasonable flag module 1 is true,
AND reasonable flag module 2 is true
```

### How this step is done, simply

The model detects conjunctions and recursively creates binary `AND` nodes. Because relations are left-associative, multiple conjuncts become a canonical nested chain.

### Output

```text
AND(
  Input-angle clause,
  AND(
    flag-1 clause,
    flag-2 clause
  )
)
```

## Step 6 - Decide that leaves are atomic

### Who performs this step

LLM guided by BUILDING-ONIONL Step 5.

### Input

Each leaf clause separately.

### How this step is done, simply

The model checks whether another unary or binary operation remains. These clauses each describe one engineering fact, so recursion stops.

### Output

Four atomic clauses:

```text
system work mode is DualINUMode
InputAngle equals weighted module angles
RationalFlag_Module1 is true
RationalFlag_Module2 is true
```

### Failure branch

If a clause is not truly atomic but lacks an obvious connective, `REFINEIMPLICITSTRUCTURE` rewrites a decomposition plan and repeats Steps 3-5.

## Step 7 - Normalize atomic propositions

### Who performs this step

LLM guided by BUILDING-ONIONL Step 6 and OnionL AP patterns.

### Input

The four atomic natural-language clauses.

### How this step is done, simply

Each clause is rewritten into a canonical predicate using component, variable, relation, and formula fields.

### Output

```yaml
atomic_propositions:
  - Var: workmode
    Rel: "="
    Formula: DualINUMode
  - Var: InputAngle
    Rel: "="
    Formula: 0.5 * Angle_Module1 + 0.5 * Angle_Module2
  - Var: RationalFlag_Module1
    Rel: "="
    Formula: True
  - Var: RationalFlag_Module2
    Rel: "="
    Formula: True
```

## Step 8 - Assemble OnionL JSON

### Who performs this step

LLM output generation plus structured-response parser.

### Input

All scope, relation, and AP nodes from Steps 2-7.

### How this step is done, simply

The nodes are nested according to the discovered hierarchy and emitted as machine-readable JSON. This is still an LLM-produced artifact and must be validated.

### Prompt used

The same unpublished grammar-constrained prompt. The exact JSON schema is not printed in full.

### Output

```json
{
  "scope": "Globally",
  "child": {
    "relation": "Implies",
    "left": {"atomic": "workmode = DualINUMode"},
    "right": {
      "scope": "Globally",
      "child": {
        "relation": "AND",
        "left": {"atomic": "InputAngle = 0.5*Angle_Module1 + 0.5*Angle_Module2"},
        "right": {
          "relation": "AND",
          "left": {"atomic": "RationalFlag_Module1 = True"},
          "right": {"atomic": "RationalFlag_Module2 = True"}
        }
      }
    }
  }
}
```

This compact schema is illustrative; the hierarchy matches Figures 3 and 4.

## Step 9 - Perform first machine validation

### Who performs this step

Deterministic OnionL validator.

### Input

OnionL JSON.

### How this step is done, simply

Depth-first traversal checks every node:

```text
Scope node   -> exactly one child
Relation node -> exactly two children
Atomic node  -> leaf only, valid fields
Nesting      -> legal OnionL pattern
AND chain    -> canonical left-associative form
```

### Prompt used

None.

### Output

Success:

```yaml
validation: OK
canonicalization_changes: []
```

Failure:

```yaml
validation: FAILED
error_type: invalid_arity
tree_path: root.right.child
suggested_fix: Add the missing right operand.
```

## Step 10 - Feed validation errors back

### Who performs this step

Controller code and Req2OnionL LLM.

### Input

Original requirement, invalid OnionL, and diagnostics.

### How this step is done, simply

The controller formats the diagnostic as feedback and asks the LLM to regenerate a corrected structure rather than translating invalid JSON.

### Prompt used

The feedback mechanism is shown architecturally, but the paper does not print the prompt. Illustrative reconstruction:

```text
The OnionL output failed structural validation at {tree_path}:
{error_type}. Suggested correction: {suggested_fix}.
Regenerate a minimally changed OnionL JSON for the original requirement.
```

### Output

Corrected OnionL returns to Step 9.

## Step 11 - Optionally visualize for human validation

### Who performs this step

Mermaid renderer and human engineer.

### Input

Machine-valid OnionL JSON.

### How this step is done, simply

1. Program code converts the tree to Mermaid syntax.
2. Mermaid renders a directed graph.
3. The engineer inspects scopes, relations, and leaves.
4. The engineer directly edits the tree or provides natural-language feedback if the meaning is wrong.

### Prompt used

None for rendering. A natural-language regeneration prompt may be used, but it is not published.

### Output

Human-approved or corrected OnionL.

### Evaluation note

Manual validation is disabled for the main RQ1/RQ2 numbers. In a separate usability case, all 13 initially wrong formulas were corrected within ten minutes using the interface.

## Step 12 - Translate leaves and operators in post-order

### Who performs this step

Deterministic OnionL2LTL code.

### Input

Validated OnionL tree.

### How this step is done, simply

Translate children before parents:

```text
Atomic predicate -> reconstructed expression
Globally(child)  -> G(child)
AND(left,right)  -> (left AND right)
Implies(left,right) -> (left -> right)
```

### Prompt used

None. This is fixed rule-based synthesis.

### Output

```text
G(workmode = DualINUMode ->
  G((InputAngle = 0.5*Angle_Module1 + 0.5*Angle_Module2)
    AND RationalFlag_Module1 = True
    AND RationalFlag_Module2 = True))
```

## Step 13 - Validate LTL syntax

### Who performs this step

Spot parser/automata framework.

### Input

Generated LTL formula.

### How this step is done, simply

Spot parses the formula and attempts to compile it into a Buchi automaton. Successful compilation counts as syntactic validity.

### Prompt used

None.

### Output

```yaml
syntax_valid: true
```

The final formula can then be consumed by a model checker such as NuSMV.

## Alternate path - Ambiguous language and human correction

The paper's Req04 contains "as soon as possible." The automated tree interprets it as Eventually:

```text
G(WaypointCmd -> (F HeadingFun AND F DevAngleLow<2))
```

An engineer determines that the first action must happen in the next state and edits the OnionL `Eventually` node to `Next`.

```text
G(WaypointCmd -> (X HeadingFun AND F DevAngleLow<2))
```

This is a semantic correction; both formulas can be syntactically valid. It demonstrates why syntax validation alone is insufficient.

## Direct baseline path

Figure 1 prints this zero-shot instruction:

```text
You are an expert in the field of formal verification, proficient in the
rules and usage of LTL formulas. Please translate the following natural
language requirement into LTL formulas.
```

The direct path is:

```text
requirement -> LLM -> LTL
```

It has no OnionL structure or deterministic composition. On the 112 industrial requirements, GPT-4o zero-shot achieves 43.8% exact match and 89.3% syntax validity, versus Req2LTL's 88.4% and 100%.

## Component contract table

| Component | Actor | Input | Transformation | Output |
|---|---|---|---|---|
| Req2OnionL prompt builder | Code | Requirement + knowledge/examples | Fill prompt | LLM request |
| Scope extractor | LLM | Requirement | Identify global context | Scope + clause |
| Recursive decomposer | LLM | Clause | Extract scopes/relations | OnionL nodes |
| AP normalizer | LLM | Atomic clause | Populate semantic fields | Canonical AP |
| OnionL serializer | LLM + parser | All nodes | Assemble hierarchy | OnionL JSON |
| Machine validator | Code | OnionL JSON | Check arity/types/nesting | OK or diagnostics |
| Visualizer | Code + Mermaid | Valid tree | Render graph | Human-readable OnionL |
| Human reviewer | Engineer | Graph + requirement | Correct semantics | Approved OnionL |
| OnionL2LTL | Rule engine | Approved tree | Post-order mapping | LTL formula |
| Syntax checker | Spot | LTL | Parse/compile | Valid or invalid |

## Final mental model

```text
The LLM peels the requirement into semantic layers.
The validator checks the layers.
The engineer may inspect the layers.
Fixed rules compile the layers into LTL.
```
