# Learning Guide: Req2LTL and OnionL

## Paper at a glance

- **Title:** *Bridging Natural Language and Formal Specification - Automated Translation of Software Requirements to LTL via Hierarchical Semantics Decomposition Using LLMs*
- **Authors:** Zhi Ma, Cheng Wen, Zhexin Su, Xiao Liang, Cong Tian, Shengchao Qin, and Mengfei Yang
- **Version:** arXiv:2512.17334v1, 19 December 2025
- **Source:** [2512.17334v1.pdf](2512.17334v1.pdf)
- **Framework:** Req2LTL
- **Intermediate language:** OnionL
- **Goal:** Translate complex natural-language requirements into Linear Temporal Logic (LTL).
- **Main industrial result:** 88.4% exact semantic match, 100% syntax validity, 99.5% atomic-proposition recall, and BLEU 0.96 with GPT-4o.

Req2LTL uses an LLM only for semantic decomposition into OnionL. Validation and final LTL construction are deterministic. The evaluated pipeline does not fine-tune a model.

## 1. Why direct NL-to-LTL translation fails

Industrial requirements contain implicit temporal language, nested conditionals, exceptions, modes, calculations, and domain assumptions. Direct LLM translation may produce syntactically valid formulas with incorrect meaning - a silent failure.

The paper demonstrates two examples:

- "will be set" implies eventuality, but GPT-4o omits `F` and makes the output immediate.
- "unless" should express a sustained condition using `U`, but GPT-4o flattens it into simultaneous negated prerequisites.

In an initial experiment on 112 aerospace requirements, zero-shot GPT-4o produces only 49 semantically correct formulas even though atomic-proposition recall is 98.5%. The model can find local facts but struggles to compose them globally.

## 2. LTL essentials

LTL describes behavior over an infinite sequence of states.

| Operator | Meaning |
|---|---|
| `NOT p` | `p` is false |
| `p AND q` | both hold |
| `p OR q` | at least one holds |
| `p -> q` | if `p`, then `q` |
| `X p` | `p` holds in the next state |
| `F p` | `p` eventually holds |
| `G p` | `p` always holds |
| `p U q` | `p` continues to hold until `q` becomes true |

Example:

```text
Natural language: Once red, the light cannot become green next.
LTL: G(red -> X NOT green)
```

## 3. Core insight

Separate the task into two parts:

1. **Local semantic interpretation:** An LLM decomposes the requirement into a hierarchical OnionL tree.
2. **Global logical synthesis:** Validated tree nodes are mapped to LTL by fixed rules.

This uses the LLM where it is strong - language interpretation and atomic facts - and removes it from final formula composition, where errors compound.

## 4. Inputs, artifacts, and outputs

### External input

- One natural-language software requirement.
- OnionL definition/knowledge repository.
- BUILDING-ONIONL decomposition procedure.
- Grammar-constrained prompt templates and few-shot examples.
- Optional human feedback after visualization.

### Intermediate artifacts

- Detected global scope.
- Main clause separated from the scope.
- Recursive scopes, relations, and atomic clauses.
- Normalized atomic propositions.
- Machine-readable OnionL JSON/tree.
- Validation diagnostics with error type, tree path, and suggested fixes.
- Optional Mermaid visualization.

### Final output

- One syntactically valid LTL formula.
- Optional validated/corrected OnionL tree for traceability and audit.

## 5. OnionL design

OnionL has three node families.

### Scopes

Unary contextual boundaries:

- temporal: Globally, Eventually, Next;
- modes: operational contexts such as "in navigation valid mode," interpreted as implication antecedents.

### Relations

Binary composition:

- logical: AND, OR, Implies;
- temporal: forms of Until, including simple precedence and sustained precedence.

### Atomic propositions

Leaf facts with semantic subfields:

- `Com`: component/subsystem;
- `Var`: variable or constant;
- `Rel`: relation such as `=`, `>`, or `<=`;
- `Formula`: value or arithmetic expression.

An OnionL expression is recursively either an atomic proposition, a scope applied to a child, or a relation between two subexpressions. Scopes bind more tightly than relations, and binary relations are left-associative.

## 6. Framework architecture

```text
Natural-language requirement
  -> Req2OnionL LLM translator
      OnionL knowledge repository
      BUILDING-ONIONL chain-of-thought
  -> OnionL JSON
  -> first machine validation
      invalid -> diagnostics/feedback -> regenerate
  -> optional Mermaid visualization and human correction
  -> OnionL2LTL rule-based translator
  -> LTL formula
```

## 7. BUILDING-ONIONL algorithm

### Stage I: macro-structure extraction

#### Step 1: identify scope and separate the clause

Detect temporal or mode scope. If no explicit scope is present, use Globally by default.

#### Step 2: construct the top level

- Temporal scope becomes the root.
- Mode scope becomes the antecedent of an implication wrapped in Globally.
- Missing scope becomes Globally around the clause.

### Stage II: recursive clause decomposition

#### Step 3: extract unary operator

If a clause contains a unary temporal scope, create a parent node and recursively process the child.

#### Step 4: split binary relation

If a logical or temporal binary connective exists, split the clause into two subtrees and recursively process both.

#### Step 5: decide atomicity

If the clause is atomic, stop. If not, refine the implicit structure and repeat Steps 3-5.

#### Step 6: normalize the atomic proposition

Map the leaf into a predefined engineering pattern and populate `Com`, `Var`, `Rel`, and `Formula`.

The Req2OnionL prompt uses OnionL as a formal knowledge base, BUILDING-ONIONL as a chain-of-thought procedure, grammar constraints, and task-specific few-shot examples. The paper does not print the complete prompt templates.

## 8. Validation

### First: machine validation

A depth-first traversal checks:

- unary nodes have exactly one child;
- binary nodes have exactly two children;
- atomic propositions occur only at leaves;
- AP fields are present and compatible;
- scope nesting matches legal patterns;
- operations are defined and noncontradictory;
- redundant deep AND chains are canonicalized to left-associative form.

Diagnostics contain the error type, tree path, and suggested correction. Invalid results can be fed back to Req2OnionL.

### Second: optional human validation

OnionL JSON is rendered as a Mermaid graph. An engineer can inspect scopes, relations, and leaves, edit an operator, or provide feedback for regeneration. This is especially important when the requirement itself is ambiguous.

The quantitative RQ1/RQ2 evaluation disables manual validation. The human workflow is evaluated separately.

## 9. Deterministic OnionL-to-LTL translation

The translator performs post-order traversal: translate children first, then the parent.

- Globally -> `G(child)`
- Eventually -> `F(child)`
- Next -> `X(child)`
- AND -> `(left AND right)`
- OR -> `(left OR right)`
- Implies -> `(left -> right)`
- Until -> `(left U right)`
- AP -> reconstruct predicate from its semantic fields

Every well-formed OnionL tree maps to one syntactically valid formula. Spot parses/checks LTL and NuSMV can consume it for model checking.

## 10. Worked example from Figure 3

The requirement says, in summary:

```text
If the system is in dual inertial navigation calculation-angle mode,
then globally:
  input angle = 0.5 * angle module 1 + 0.5 * angle module 2,
  and both module reasonable flags are true.
```

OnionL identifies:

```text
G
└── Implies
    ├── workmode = DualINUMode
    └── G
        └── AND
            ├── InputAngle = 0.5*Angle_Module1 + 0.5*Angle_Module2
            └── AND
                ├── RationalFlag_Module1 = True
                └── RationalFlag_Module2 = True
```

The rule-based result is:

```text
G(workmode = DualINUMode ->
  G((InputAngle = 0.5*Angle_Module1 + 0.5*Angle_Module2)
    AND RationalFlag_Module1 = True
    AND RationalFlag_Module2 = True))
```

This example shows why hierarchy matters: the mode triggers an implication, while the inner Globally and conjunction apply only to the consequent.

## 12. Evaluation setup

### Academic data

Three public lifted benchmarks:

- Circuit
- Navigation
- Office Email

Atomic propositions are replaced with placeholders such as `Prop1`.

### Industrial data

112 requirements from two aerospace systems:

- sun-search controller;
- propulsion-management system.

Properties:

| Measure | Industrial | Academic |
|---|---:|---:|
| Average sentence length | 43.7 tokens | 15.3 tokens |
| At least two nesting layers | 63.2% | 9.8% |
| Average APs | 3.7 | 2.1 |

Two of five experts independently translated each requirement. Disagreements were discussed and final formulas reviewed by a senior engineer. Requirements with explicit quantitative timing or no temporal constraint were excluded because ordinary LTL cannot express them appropriately.

### Models and baselines

- GPT-4o and DeepSeek-V3.
- Zero-shot direct translation.
- NL2LTL.
- NL2SPEC.
- NL2TL.

### Metrics

- **Syntax validity:** Spot can parse/compile the formula into a Buchi automaton.
- **Exact match:** two experts agree on semantic/logical equivalence to the reference for industrial data; the academic evaluation uses strict string-level binary accuracy.
- **AP recall:** fraction of gold atomic propositions present.
- **BLEU:** token-level structural similarity after AP abstraction.

## 13. Results

### Academic benchmarks with GPT-4o

| Domain | Req2LTL binary accuracy | BLEU |
|---|---:|---:|
| Circuit | 95.3% | 0.97 |
| Navigation | 94.5% | 0.97 |
| Office Email | 96.7% | 0.98 |

NL2TL slightly exceeds Req2LTL binary accuracy on Circuit and Navigation, but Req2LTL has the strongest or tied structural similarity. The main gains appear on complex industrial data.

### Industrial requirements

| Model + method | Exact match | Syntax validity | AP recall | BLEU |
|---|---:|---:|---:|---:|
| GPT-4o zero-shot | 43.8% | 89.3% | 98.5% | 0.76 |
| GPT-4o NL2TL | 65.2% | 94.6% | 98.1% | 0.85 |
| GPT-4o Req2LTL | **88.4%** | **100.0%** | **99.5%** | **0.96** |
| DeepSeek-V3 zero-shot | 34.8% | 87.5% | 97.5% | 0.73 |
| DeepSeek-V3 Req2LTL | **86.6%** | **100.0%** | **99.2%** | **0.96** |

High AP recall for weak baselines reinforces the paper's diagnosis: extracting facts is easy; arranging temporal scope and nesting is hard.

## 14. Ablation study

| Configuration | Exact match | Syntax validity | BLEU |
|---|---:|---:|---:|
| Full Req2LTL | 88.4% | 100.0% | 0.96 |
| No structured OnionL | 65.2% | 98.2% | 0.86 |
| No stage-wise decomposition | 58.9% | 94.6% | 0.85 |
| No verification feedback | 84.8% | 90.2% | 0.91 |

Stage-wise decomposition has the largest semantic impact. Validation feedback chiefly protects syntax and structural correctness. OnionL and staged prompting are mutually reinforcing.

## 15. Error analysis and human correction

The authors classify errors as temporal misinterpretation, conditional confusion, loss of nesting, incorrect AP binding, and ambiguity/context omission. Req2LTL eliminates the first four categories in the reported Figure 5 comparison; its remaining ten errors arise from ambiguity/context omission.

One example says to initiate heading adjustment "as soon as possible." The model maps this to Eventually, but experts intend Next:

```text
Incorrect: G(WaypointCmd -> (F HeadingFun AND F DevAngleLow<2))
Correct:   G(WaypointCmd -> (X HeadingFun AND F DevAngleLow<2))
```

Thirteen erroneous formulas among 112 requirements were corrected through the visual interface within ten minutes. These corrections are not included in the automated RQ1/RQ2 scores.

## 16. Contributions

1. OnionL, a hierarchical semantic intermediate language.
2. BUILDING-ONIONL, a two-stage, six-step decomposition procedure.
3. Combination of LLM semantic parsing with deterministic formal synthesis.
4. Automated structural validation and optional visual human feedback.
5. Strong academic and aerospace evaluation across two LLM backends.

## 17. Limitations

- Industrial data and full source code cannot currently be released.
- Generalization beyond aerospace is untested.
- Results depend on LLM version/provider behavior.
- Public academic benchmarks may occur in model training data.
- Ambiguous requirements still need domain expertise.
- Ordinary LTL cannot express explicit quantitative timing; such requirements were excluded.
- Semantic correctness is guaranteed only if OnionL faithfully captures the requirement.
- Exact production prompts and few-shot demonstrations are not published.

## 18. Reproduction outline

1. Define OnionL node types, legal patterns, and AP schemas.
2. Implement BUILDING-ONIONL prompting with staged decomposition and few-shot examples.
3. Parse the LLM response into OnionL JSON.
4. Validate arity, node position, fields, nesting, and canonical form.
5. Optionally render Mermaid and collect corrections.
6. Translate by post-order fixed rules.
7. Validate LTL with Spot.
8. Compare with expert references using syntax, semantic match, AP recall, and BLEU.

## 19. Compact mental model

```text
Natural language
  -> LLM builds a transparent semantic tree
  -> machine/human validates the tree
  -> fixed rules compile the tree into LTL
```

The central claim is that **LLMs should discover semantic structure, while deterministic code should assemble formal logic**.

## 20. Glossary

- **LTL:** Linear Temporal Logic.
- **AP:** Atomic proposition.
- **OnionL:** Hierarchical intermediate tree of scopes, relations, and APs.
- **Req2OnionL:** LLM-based natural-language-to-OnionL module.
- **OnionL2LTL:** Validation and rule-based compilation module.
- **Spot:** LTL and omega-automata parsing/manipulation framework.
- **NuSMV:** Symbolic model checker.
- **Silent failure:** Syntactically valid but semantically wrong formula.
