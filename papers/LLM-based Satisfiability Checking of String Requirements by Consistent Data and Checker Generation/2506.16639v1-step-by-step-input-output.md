# Step-by-Step Input and Output Guide

## Paper

This guide explains the data flow in *LLM-based Satisfiability Checking of String Requirements by Consistent Data and Checker Generation*.

- [Source paper](2506.16639v1.pdf)
- [Full learning guide](2506.16639v1-explained.md)

The goal here is narrow: show **what enters and leaves every step** of the proposed method.

The running example uses the paper's email requirements and example strings. The checker code and retry transcript below are a pedagogical reconstruction of how the method operates. They are not presented as a verbatim log from the authors' implementation.

---

## Important clarification about prompts

The paper does **not** publish a complete set of messages explicitly labeled `system`, `user`, and `assistant` for every LLM call.

What the paper actually provides is:

| LLM operation | What the paper provides | Is the complete system prompt printed? |
|---|---|---:|
| Generate Python checkers | A description of the zero-shot prompt: Python function signature plus a docstring containing the NL requirement | No |
| Generate SMT checkers | A description of the one-shot prompt: requirements plus one NL-to-SMT example, requesting exactly one SMT expression per requirement | No |
| Repair invalid checkers | A description of feeding soundness feedback back to the checker generator | No |
| Generate or repair the LVO | A visible **prompt-template excerpt** in Figure 3 | Partly; the excerpt is printed, but the paper does not identify it specifically as a system-role message or show the complete serialized prompt |

The authors say the prompts also use a role description, chain-of-thought instructions, and emotional-stimulus wording. Structured output is handled with LangChain. When this guide shows a prompt that is not printed in the paper, it is labeled **illustrative reconstruction**.

### Figure 3 prompt-template excerpt

The following is the prompt structure shown in Figure 3, formatted for readability. It is the closest thing to a published verifier prompt in the paper:

```text
You are a test engineer working on creating test data for a new feature.
You are given a variable "{name}" with some associated constraints.

Your target is to find a string value for "{name}" that satisfies ALL
of the following constraints:
{constraints}

If the word "{name}" is meaningful, the value should be as realistic
as possible.

Before proposing a candidate value, analyze whether the constraints are
logically consistent. If any constraints conflict, explain which ones
and conclude that no value can satisfy all constraints (output "UNSAT").

Below are previously generated values for "{name}" provided as counterexamples.
These values do not satisfy all constraints:
{update_feedback}

Your output should follow the format below. If no value can satisfy all
constraints, assign the value "UNSAT":
{output_format}

Please follow these steps:
1. Summarize Counter Example Violations: ...
2. Analyze the Constraints: ...
3. Determine Feasibility: ...
```

The ellipses are present because Figure 3 is explicitly an excerpt. Therefore, this guide should not claim that the paper reveals the complete production system prompt.

## 1. The running example

The system receives one string variable named `email` and three natural-language requirements:

```text
R1: The system shall require an email address to contain exactly one "@" character.

R2: The system shall require an email address not to end with a "." character.

R3: The system shall require an email to contain at least one "." character after the "@" character.
```

The question is:

```text
Does at least one string satisfy R1 AND R2 AND R3?
```

For this example, the correct answer is SAT because `ab@cd.com` satisfies all three requirements.

### End-to-end view

```text
Natural-language requirements
        |
        v
Split into batches
        |
        v
Generate one Python and/or SMT checker per requirement
        |
        v
Validate and repair generated checkers
        |
        v
Merge the checkers
        |
        v
Ask a verifier LLM for UNSAT or SAT + candidate string
        |
        v
Validate the LLM outcome with the generated checkers
        |
        +---- correct ----> return SAT + data or UNSAT
        |
        +---- incorrect --> create feedback and retry
        |
        +---- unknown ----> return UNKNOWN + best saved result
```

## 2. Step 0 - Receive and normalize the task

### Input

```yaml
variable_name: email
requirements:
  - id: R1
    text: The email address must contain exactly one "@" character.
  - id: R2
    text: The email address must not end with a "." character.
  - id: R3
    text: The email must contain at least one "." after the "@" character.
```

### What the step does

It identifies:

- the string variable being constrained;
- the individual requirements;
- whether each requirement is positive or negated;
- the complete condition, which is the logical AND of all requirements.

No satisfiability decision has been made yet.

### How this step is done, simply

The requirements already arrive as the method's input. Ordinary program code stores the variable name and keeps the requirements as an ordered list. It may assign identifiers such as `R1`, `R2`, and `R3` so later checker results can be traced back to the correct sentence.

This is **not described as an LLM step** in the paper. The YAML structure in this guide is only a convenient way to visualize the input; the paper does not require this exact schema and provides no prompt for normalization.

### Output

```yaml
variable:
  name: email
  type: string
condition:
  operator: AND
  operands: [R1, R2, R3]
```

This normalized representation becomes the input to both the checker generator and, later, the verifier LLM.

## 3. Step 1 - Split the requirements into checker-generation batches

The checker generator does not have to translate all requirements in one prompt. It first creates batches.

### Input

```text
[R1, R2, R3]
```

### How this step is done, simply

Normal control code slices the requirement list according to a configured policy:

```python
if strategy == "IND":
    batches = [[requirement] for requirement in requirements]
else:
    batches = [positive_requirements, negated_requirements]
```

No LLM is needed. It is a deterministic list-grouping operation, so the paper provides no system prompt for this step.

### Option A: IND splitting

IND means that every requirement is handled independently.

### Output

```yaml
batches:
  - batch_id: B1
    requirements: [R1]
  - batch_id: B2
    requirements: [R2]
  - batch_id: B3
    requirements: [R3]
```

The paper finds that IND generally improves SMT checker generation because each LLM call solves a smaller translation problem.

### Option B: BATCH splitting

In the experiment, BATCH groups positive requirements together and negated requirements together. Because this example contains only positive requirements, its positive batch would be:

```yaml
batches:
  - batch_id: positive_requirements
    requirements: [R1, R2, R3]
```

### Output passed to the next step

For the remainder of this guide, assume the system selects IND:

```text
B1 = [R1]
B2 = [R2]
B3 = [R3]
```

## 4. Step 2A - Generate imperative Python checkers

For each requirement batch, the LLM receives a function signature and the requirement as a docstring or function description.

### How this step is done, simply

1. Program code creates a Python function stub.
2. It inserts the current natural-language requirement into the docstring.
3. It sends that text to an LLM once, without a worked Python example; this is zero-shot prompting.
4. The LLM completes the function implementation.
5. LangChain parses the model's structured response so the checker can be saved and validated.

The LLM performs the natural-language-to-code translation. The surrounding program performs template filling, API invocation, response parsing, and later validation.

### Does the paper provide this system prompt?

No. The paper describes its ingredients but does not print the full prompt or separate it into system and user messages. A prompt consistent with the paper's description would have the following **illustrative reconstruction**:

```text
Role: You are a software test engineer who writes Python validation functions.

Task: Complete the following function so it returns True exactly when the
input string satisfies the requirement in its docstring. Return the checker
in the required structured format.

def check_r1(s: str) -> bool:
    """The email address must contain exactly one '@' character."""
```

Only the signature-plus-docstring design is stated by the paper. The precise role wording above is not printed in it.

### Input for R1

```python
def check_r1(s: str) -> bool:
    """Return True only if the email contains exactly one '@' character."""
```

### LLM transformation

The LLM completes the function body.

### Output for R1

```python
def check_r1(s: str) -> bool:
    return s.count("@") == 1
```

### Inputs and outputs for all three requirements

```python
def check_r1(s: str) -> bool:
    """Exactly one '@'."""
    return s.count("@") == 1


def check_r2(s: str) -> bool:
    """Must not end with '.'."""
    return not s.endswith(".")


def check_r3(s: str) -> bool:
    """At least one '.' must occur after the '@'."""
    at_index = s.find("@")
    return at_index != -1 and "." in s[at_index + 1:]
```

Each function has the same interface:

```text
Input:  one concrete string s
Output: True if s satisfies this one requirement; otherwise False
```

### Concrete executions

| Checker call | Output | Meaning |
|---|---:|---|
| `check_r1("ab@cd.com")` | `True` | Exactly one `@` exists. |
| `check_r2("ab@cd.com")` | `True` | The value does not end with `.`. |
| `check_r3("ab@cd.com")` | `True` | A `.` occurs after `@`. |
| `check_r1("ab@@cd.com")` | `False` | Two `@` characters exist. |
| `check_r2("ab@cd.")` | `False` | The value ends with `.`. |
| `check_r3("ab@cdcom")` | `False` | There is no `.` after `@`. |

### What Python can and cannot output

Python can answer this question:

```text
Does this specific candidate string satisfy the requirement?
```

Python cannot generally answer this question:

```text
Is it impossible for every possible string to satisfy all requirements?
```

That second question requires declarative solving in this method.

## 5. Step 2B - Generate declarative SMT checkers

The SMT-generation prompt contains the requirement, an example natural-language-to-SMT translation, and instructions to return one SMT expression per requirement.

### How this step is done, simply

1. Program code selects the current requirement batch.
2. It fills a prompt with that batch and one example showing how natural language maps to an SMT expression.
3. The LLM translates each requirement into symbolic string logic.
4. The response parser extracts exactly one expression for each requirement.
5. The expressions are sent to an SMT parser before they are trusted.

This is one-shot prompting because the prompt contains one demonstration.

### Does the paper provide this system prompt?

No. The paper describes the prompt structure but does not print the actual example pair or complete system/user messages. The following is an **illustrative reconstruction** of the described structure:

```text
Role: You translate natural-language string requirements into SMT expressions.

Example requirement:
<one example natural-language requirement>

Example output:
<its SMT checker expression as a string>

Requirements to translate:
{current_requirement_batch}

Produce exactly one SMT expression string for each requirement and follow the
required structured output format. Analyze each requirement before answering.
```

The placeholders matter: the PDF does not reveal the concrete demonstration used in the experiment.

### Input for R1

```text
Requirement:
The email address must contain exactly one "@" character.

Output exactly one SMT string expression representing this requirement.
```

### Output for R1

The paper shows this form of checker for R1:

```text
(and
  (str.contains s "@")
  (not
    (str.in_re s
      (re.++
        (re.* re.allchar)
        (str.to_re "@")
        (re.* re.allchar)
        (str.to_re "@")
        (re.* re.allchar)))))
```

It says:

1. `s` contains an `@`;
2. `s` does not match a pattern containing two `@` characters.

Together, those statements mean exactly one `@`.

### Illustrative outputs for R2 and R3

```text
R2:
(not (= (str.at s (- (str.len s) 1)) "."))

R3:
(and
  (>= (str.indexof s "@" 0) 0)
  (>= (str.indexof s "." (+ (str.indexof s "@" 0) 1)) 0))
```

These expressions are pedagogical equivalents, not claimed to be the exact strings produced in the experiment.

Each declarative checker has this conceptual interface:

```text
Input:  a symbolic string variable s
Output: a logical expression describing every s that satisfies the requirement
```

Unlike a Python checker, an SMT expression can participate in a search for a model or a proof that no model exists.

## 6. Step 3 - Check the generated checkers

The generated checker is itself an untrusted LLM output. The system therefore validates it before using it to judge the verifier LLM.

### How this step is done, simply

This step is performed by ordinary tools, not by an LLM:

- A Python parser or interpreter tries to parse the Python function.
- An SMT parser tries to parse the SMT expression.
- If labeled examples are available, a test runner executes the checker on each example and compares actual results with expected results.
- If a ground-truth SMT expression is available, CVC5 can try to prove that the generated and reference expressions are equivalent.

The tool outputs are converted into statuses such as `SOUND`, `UNSOUND`, `PASS`, or `FAIL`. Because the checking is performed by parsers, execution, tests, and a solver, there is no system prompt for this step.

### Input

```yaml
batch_id: B2
natural_language_requirement: R2
generated_python_checker: |
  def check_r2(s: str) -> bool:
      return not s.endswith(".")
generated_smt_checker: |
  (not (= (str.at s (- (str.len s) 1)) "."))
```

### Syntactic validation

The appropriate parser tries to parse the checker.

Example successful output:

```yaml
checker_id: R2-Python
syntax_status: SOUND
parser_errors: []
```

Example failed output:

```yaml
checker_id: R2-Python
syntax_status: UNSOUND
parser_errors:
  - "SyntaxError: expected ':' after function definition"
```

### Optional semantic validation

When labeled samples or a trusted reference implementation are available, a checker can also be tested semantically.

Example test input:

```yaml
requirement: R2
samples:
  - value: "ab@cd.com"
    expected: true
  - value: "ab@cd."
    expected: false
```

Example output:

```yaml
checker: check_r2
sample_results:
  - value: "ab@cd.com"
    actual: true
    matches_expected: true
  - value: "ab@cd."
    actual: false
    matches_expected: true
semantic_test_status: PASS
```

In the study, semantic quality is evaluated using five satisfying and five violating samples per requirement. SMT checkers can additionally be compared with ground-truth SMT expressions through formal equivalence checking.

## 7. Step 4 - Repair an invalid checker

If a checker fails validation, the diagnostics are returned to the checker-generation LLM.

### How this step is done, simply

1. The validator identifies which checker failed and records the error.
2. Program code inserts the original requirement, failed checker, and diagnostic into a retry prompt.
3. The same checker-generation LLM is called again.
4. Only the failed checker needs to be regenerated.
5. The new checker goes back through Step 3.

### Does the paper provide the repair prompt?

No. It says soundness feedback is gathered and fed back into the LLM-based converter, but it does not print the retry prompt. The feedback block already shown below is an **illustrative reconstruction** consistent with that description.

### First generated output

```python
def check_r2(s: str) -> bool
    return not s.endswith(".")
```

This function is missing the colon after `bool`.

### Feedback input to the LLM

```text
The generated checker for R2 is syntactically invalid.
Parser feedback: expected ':' after the function definition.
Regenerate only the checker for R2.
```

### Repaired output

```python
def check_r2(s: str) -> bool:
    return not s.endswith(".")
```

### Step result

```yaml
checker_id: R2-Python
attempt: 2
syntax_status: SOUND
```

The paper's experiment allows at most two LLM calls for checker generation.

## 8. Step 5 - Merge all sound checkers

After every individual batch passes the configured validation, the batches are combined.

### How this step is done, simply

Program code waits until each batch has a soundness status. It then concatenates the batch results or stores them in a dictionary keyed by requirement identifier. No new reasoning or code generation occurs.

```python
all_checkers = {}
for sound_batch in sound_batches:
    all_checkers.update(sound_batch.checkers)
```

This is a deterministic bookkeeping step, so there is no LLM system prompt.

### Input

```yaml
sound_batches:
  - B1: [check_r1]
  - B2: [check_r2]
  - B3: [check_r3]
```

### Output

```yaml
verification_outcome_checkers:
  imperative:
    R1: check_r1
    R2: check_r2
    R3: check_r3
  declarative:
    R1: smt_r1
    R2: smt_r2
    R3: smt_r3
```

This merged checker set and the original natural-language requirements become the two main inputs to the verifier.

## 9. Step 6 - Ask the verifier LLM for an outcome

The verifier LLM receives all requirements at once because it must reason about their conjunction.

### How this step is done, simply

1. Program code fills `{name}` with `email`.
2. It fills `{constraints}` with R1, R2, and R3.
3. On the first attempt, `{update_feedback}` is empty.
4. It supplies the structured `{output_format}` expected by LangChain.
5. The LLM reasons about the combined requirements.
6. It returns either a candidate string or `UNSAT`.
7. LangChain converts that response into an LVO object that the verifier can inspect.

This is an LLM step. The paper uses zero-shot prompting for requirement verification and prints the template excerpt reproduced near the beginning of this guide. It does not label that text specifically as an API `system` message.

### Filled prompt for the running example

```text
You are a test engineer working on test data for a variable named "email".

Find a realistic string that satisfies ALL constraints:
1. Exactly one "@" character.
2. Must not end with ".".
3. At least one "." after the "@".

Previously generated counterexamples:
<none on the first attempt>

Analyze whether the constraints are logically consistent. If they conflict,
explain the conflict and output UNSAT. Otherwise return a realistic candidate
using the required structured output format.
```

This filled version is a shortened, readable instantiation of Figure 3, not a claim about the exact serialized API message.

### Possible output A: SAT candidate

```yaml
decision: SAT
data: "ab@cd."
```

This is only an **LLM-derived verification outcome**, abbreviated LVO. It is not yet trusted. Notice that the candidate actually violates R2.

### Possible output B: UNSAT claim

```yaml
decision: UNSAT
data: null
```

This is also untrusted until the declarative checker confirms it.

## 10. Step 7A - Validate a `SAT + data` outcome

Assume the first LVO is:

```yaml
decision: SAT
data: "ab@cd."
```

### How this step is done, simply

The verifier calls every checker with the same candidate. For Python, this is equivalent to:

```python
results = {
    "R1": check_r1(candidate),
    "R2": check_r2(candidate),
    "R3": check_r3(candidate),
}

correct = all(results.values())
quality = sum(results.values()) / len(results)
violations = [name for name, passed in results.items() if not passed]
```

The SMT version binds symbolic variable `s` to the concrete candidate and asks whether the resulting constraints are satisfiable. These are executable checker operations, not LLM calls, so no prompt is used.

### Input to the checkers

```text
candidate s = "ab@cd."
```

### Per-requirement outputs

```yaml
R1:
  checker_output: true
  reason: exactly one "@"
R2:
  checker_output: false
  reason: candidate ends with "."
R3:
  checker_output: true
  reason: a "." occurs after "@"
```

### Combined output

```yaml
correctness: INCORRECT
requirements_satisfied: 2
total_requirements: 3
quality: 0.667
violated_requirements: [R2]
```

The current candidate cannot be returned because every requirement must be satisfied.

Both Python and SMT can check a concrete candidate. Python is especially useful here because it can directly execute expressive string logic.

## 11. Step 7B - Validate an `UNSAT` outcome

Suppose the verifier instead claims:

```yaml
decision: UNSAT
```

### How this step is done, simply

Program code joins the generated SMT expressions with logical AND and submits the result to the solver. It does **not** provide a concrete value for `s`.

```text
assert R1(s)
assert R2(s)
assert R3(s)
check-sat
```

- Solver output `unsat` confirms the LLM claim.
- Solver output `sat` disproves the claim because at least one string exists.
- Solver output `unknown` establishes neither result.

The solver follows formal commands rather than a natural-language system prompt.

### Input to the SMT solver

```text
smt_r1 AND smt_r2 AND smt_r3
```

### Solver output for this example

```yaml
solver_result: SAT
example_model: "ab@cd.com"
```

### Correctness output

```yaml
lvo: UNSAT
correctness: INCORRECT
```

The LLM's UNSAT claim is wrong because the solver found a satisfying model.

The method does not return the solver's model as final user-facing data. The authors want the LLM to generate realistic data, and a generated SMT checker may itself be imperfect. The model is used to invalidate the UNSAT claim, after which the LLM gets another attempt.

### Why Python is not used on this branch

There is no candidate string to pass into a Python function. Python can reject examples one at a time, but that does not prove that **all possible strings** fail. The declarative SMT checker is therefore necessary for validating UNSAT.

## 12. Step 8 - Save the failed LVO and produce feedback

For the failed candidate `ab@cd.`, the system saves both its score and its violations.

### How this step is done, simply

Ordinary program code stores the failed outcome and checker results in a list. It then formats the next prompt according to the selected feedback level:

```python
saved_lvos.append({
    "value": candidate,
    "quality": quality,
    "violations": violations,
})

if feedback_mode == "V":
    feedback = "The previous output was invalid."
elif feedback_mode == "VF":
    feedback = format_failed_values(saved_lvos)
elif feedback_mode == "VFE":
    feedback = format_values_and_violations(saved_lvos)
```

No LLM is required to discover the violations: the individual checker outputs already identify them. The resulting text is inserted into Figure 3's `{update_feedback}` placeholder on the next LLM call.

### Input

```yaml
lvo:
  decision: SAT
  data: "ab@cd."
checker_results:
  R1: true
  R2: false
  R3: true
```

### Saved output

```yaml
saved_lvo:
  decision: SAT
  data: "ab@cd."
  quality: 0.667
  violated_requirements: [R2]
```

The amount of information sent back depends on the feedback configuration.

### +V: validation only

```text
The previous output was invalid. Try again.
```

### +VF: validation with failed value

```text
The following previous value did not satisfy all constraints:
"ab@cd."
Try again.
```

### +VFE: validation with failed value and explanation

```text
The following previous value did not satisfy all constraints:
"ab@cd."

Violation:
R2 failed because the value ends with ".".

Generate a new value that satisfies every requirement.
```

The paper finds that +VFE is generally the strongest overall feedback configuration because it tells the LLM what must be repaired.

## 13. Step 9 - Retry verification

### How this step is done, simply

The framework checks whether the retry budget remains. If it does, it calls the verifier LLM again with the same requirements and the newly filled feedback field. This is not a separate kind of model; it is another inference call using the updated prompt.

The paper provides the same Figure 3 prompt-template excerpt for this feedback-enabled LVO generation. The concrete counterexample and violation text below are inserted into `{update_feedback}`.

### Input

The verifier receives:

```yaml
original_requirements: [R1, R2, R3]
counterexample: "ab@cd."
violation_explanation:
  - R2: The value ends with ".".
remaining_budget: true
```

### New LLM output

```yaml
decision: SAT
data: "ab@cd.com"
```

### Checker outputs

```yaml
R1: true
R2: true
R3: true
```

### Correctness output

```yaml
correctness: CORRECT
```

### Final output

```yaml
verification_outcome: SAT
data: "ab@cd.com"
```

The concrete string is the proof of satisfiability.

## 14. A complete UNSAT example from the paper

Now consider the condition:

```text
R1 AND NOT R2 AND NOT R3
```

Expand the meanings:

```text
R1:     exactly one "@"
NOT R2: the string ends with "."
NOT R3: there is no "." after "@"
```

These conditions conflict. If there is exactly one `@` and the string ends with `.`, then that final `.` occurs after the `@`. That contradicts `NOT R3`.

### How this path is done, simply

The checker generator first creates declarative expressions for `R1`, `NOT R2`, and `NOT R3`. The verifier LLM receives their natural-language forms and proposes `UNSAT`. The surrounding program then asks the SMT solver to solve the conjunction. Because the solver returns `unsat`, the program accepts and returns the LLM's claim.

The only natural-language prompt on this path is the verifier template from Figure 3, filled with the three requirements. Checker-generation prompts follow the structures described in Steps 2A and 2B; the paper does not print their complete text.

### Step input

```yaml
requirements: [R1, NOT_R2, NOT_R3]
```

### Verifier LLM output

```yaml
decision: UNSAT
```

### Declarative checker input

```text
smt_r1 AND smt_not_r2 AND smt_not_r3
```

### SMT solver output

```yaml
solver_result: UNSAT
```

### Final system output

```yaml
verification_outcome: UNSAT
data: null
```

This final output is accepted because the declarative checker confirms the LLM's claim.

## 15. What happens when the checker returns `UNKNOWN`?

An SMT solver may time out or return `unknown` for difficult string constraints. In that case, it has neither confirmed nor refuted the LVO.

### How this step is done, simply

This is an `if` branch in the verifier controller. When the solver reports `unknown`, the system does not tell the LLM that its answer was wrong, because that has not been established. Instead, code examines the already saved LVOs and selects the closest-to-sound one using the rules below.

No LLM prompt is used for the selection itself.

### Input

```yaml
lvo:
  decision: UNSAT
checker_result: UNKNOWN
saved_lvos:
  - decision: SAT
    data: candidate_A
    quality: 0.75
  - decision: SAT
    data: candidate_B
    quality: 0.90
  - decision: UNSAT
```

### Selection logic

- If saved UNSAT outcomes outnumber saved SAT outcomes, select `~UNSAT`.
- Otherwise, select the SAT candidate satisfying the highest fraction of requirements.

### Output for the example above

```yaml
verification_outcome: UNKNOWN
best_saved_lvo:
  approximate_decision: "~SAT"
  data: candidate_B
  quality: 0.90
```

`~SAT` and `~UNSAT` are guesses attached to an `UNKNOWN` result. They are not verified conclusions.

## 16. What happens when the retry budget expires?

The experiment allows up to five verifier LLM calls.

### How this step is done, simply

After each incorrect LVO, a counter is increased. Before another LLM call, the controller compares that counter with the configured maximum:

```python
if verifier_calls < 5:
    retry_with_feedback()
else:
    return unknown_with_best_saved_lvo()
```

The final selection uses stored decisions and quality scores, not another LLM call. Therefore, no system prompt is needed after the budget has expired.

### Input

```yaml
remaining_budget: false
saved_lvos:
  - decision: SAT
    data: "ab@cd."
    quality: 0.667
  - decision: SAT
    data: "ab@cdcom"
    quality: 0.667
  - decision: UNSAT
```

There are more saved SAT candidates than UNSAT claims. The system therefore chooses the highest-quality SAT candidate. If candidates tie, the paper does not specify a detailed tie-breaking rule.

### Output

```yaml
verification_outcome: UNKNOWN
best_saved_lvo:
  approximate_decision: "~SAT"
  data: "ab@cd."
  quality: 0.667
```

This graceful degradation gives the user the best attempt while honestly reporting that correctness was not established.

## 17. Input/output contract for every component

| Component | Input | Output |
|---|---|---|
| Requirement splitter | Complete list of NL requirements | Requirement batches |
| Python checker generator | One batch plus Python signature/docstring prompt | Boolean Python functions |
| SMT checker generator | One batch plus example translation and format instructions | SMT string expressions |
| Syntax evaluator | Generated checker | `SOUND` or `UNSOUND` plus parser feedback |
| Semantic test evaluator | Checker plus labeled sample strings | Per-sample results and pass/fail |
| Formal equivalence evaluator | Generated and ground-truth SMT expressions | Equivalent, not equivalent, or solver unknown/timeout |
| Checker merger | All sound checker batches | One checker collection indexed by requirement |
| Verifier LLM | All NL requirements plus optional prior feedback | `UNSAT` or `SAT + data` LVO |
| Candidate evaluator | `SAT + data` plus Python/SMT checkers | Correct, incorrect, or unknown; violated requirements; quality |
| UNSAT evaluator | `UNSAT` plus SMT checker conjunction | Correct, incorrect, or unknown |
| Feedback builder | Failed LVO plus checker results | Retry prompt content at +V, +VF, or +VFE detail |
| Budget controller | Attempt count or other budget measure | Retry or stop |
| Best-LVO selector | Saved failed LVOs and their scores | `~SAT` with best candidate or `~UNSAT` |
| Whole system | NL requirements over one string | Confirmed SAT + realistic witness, confirmed UNSAT, or UNKNOWN + approximation |

## 18. The most important data-flow distinction

There are three different objects that are easy to confuse:

### Natural-language requirement

```text
The email must contain exactly one "@".
```

This is understandable to people and LLMs but is not directly executable by a solver.

### Checker

```python
return s.count("@") == 1
```

This is the executable interpretation of the requirement. It decides whether a candidate obeys that one rule.

### Verification outcome

```yaml
decision: SAT
data: "ab@cd.com"
```

This is the proposed answer for the conjunction of all requirements.

The checker is not the answer. It is the mechanism used to decide whether the answer should be trusted.

## 19. Final mental model

For a SAT case:

```text
NL requirements
    -> generated checkers
    -> LLM candidate string
    -> all checkers return true
    -> SAT + candidate string
```

For an UNSAT case:

```text
NL requirements
    -> generated SMT checkers
    -> LLM claims UNSAT
    -> SMT solver proves checker conjunction UNSAT
    -> UNSAT
```

For an unsuccessful search:

```text
NL requirements
    -> several failed LVOs
    -> checker feedback and retries
    -> budget exhausted or checker unknown
    -> UNKNOWN + best approximate LVO
```

The central idea is simple: **an LLM proposes, executable checkers judge, and detailed failures guide the next proposal.**
