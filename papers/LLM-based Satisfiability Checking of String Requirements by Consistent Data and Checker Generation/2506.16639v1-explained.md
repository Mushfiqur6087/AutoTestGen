# Learning Guide: LLM-based Satisfiability Checking of String Requirements

## Paper at a glance

- **Title:** *LLM-based Satisfiability Checking of String Requirements by Consistent Data and Checker Generation*
- **Authors:** Boqi Chen, Aren A. Babikian, Shuzhao Feng, Daniel Varro, and Gunter Mussbacher
- **Version:** arXiv:2506.16639v1, 19 June 2025
- **Source PDF:** [2506.16639v1.pdf](2506.16639v1.pdf)
- **Core question:** Given several natural-language requirements about one string, can a system decide whether all requirements can hold simultaneously and, when they can, produce a realistic example string?
- **Core idea:** Let an LLM propose an answer, but do not trust that answer directly. Use a second LLM-driven process to translate the requirements into executable checkers, use those checkers to validate the proposed answer, and feed any failure information back to the proposing LLM.

This is an **inference-time orchestration method**, not a new model architecture and not a fine-tuning method. The authors use existing LLMs through prompts and combine them with Python execution and SMT solving.

---

## 1. What problem is the paper solving?

Software often manipulates strings: email addresses, passwords, URLs, dates, ISBNs, file paths, arithmetic expressions, DNA sequences, and so on. A string may need to obey many requirements at the same time. For example:

1. An email contains exactly one `@`.
2. It does not end with `.`.
3. It contains at least one `.` after the `@`.

The task is to answer whether the **conjunction** of all requirements is satisfiable:

```text
There exists a string s in Sigma* such that:
R1(s) AND R2(s) AND ... AND Rn(s)
```

Here, `s` is a finite string, `Sigma*` is the set of all possible finite strings over an alphabet, and each `Ri` is one requirement.

There are two useful outcomes:

- **SAT:** At least one string satisfies every requirement. A concrete string is a constructive proof.
- **UNSAT:** No string can satisfy every requirement.

This matters for requirements engineering and test generation. If a test condition is SAT, its satisfying string can become test data. If it is UNSAT, the test condition is impossible and should not be used.

### Why neither LLMs nor formal solvers are enough by themselves

An LLM understands natural language and can generate realistic values, but it can make reasoning mistakes and offers no soundness guarantee.

An SMT solver can reason rigorously over a formal constraint, but the natural-language requirements first have to be translated into a formal language such as SMT-LIB. That translation usually needs formal-methods expertise. String solvers can also time out or return `unknown` for difficult features such as recursion and quantification.

Python is expressive and convenient for checking a **given candidate**, but a Python predicate cannot generally prove that no candidate exists. This asymmetry is the reason for the paper's hybrid design.

## 2. Exact inputs and outputs

### 2.1 External input

The system receives:

- a variable name, such as `email`, `password`, or `isbn`;
- a collection of natural-language requirements about that one string variable;
- a retry budget, expressed as a limit on LLM calls, tokens, or time;
- configuration choices: checker type, requirement batching strategy, and feedback detail.

Conceptually, the input is:

```text
Variable: email
Requirements:
  R1: The email must contain exactly one "@".
  R2: The email must not end with ".".
  R3: The email must contain at least one "." after the "@".
```

Requirements can also be negated. This lets the method represent test partitions such as `R1 AND NOT R2 AND R3`, not merely the normal valid-input case.

### 2.2 Intermediate artifacts

The system generates two kinds of checker for each requirement.

**Imperative checker (Python):**

```python
def requirement_1(s: str) -> bool:
    return s.count("@") == 1
```

It maps a concrete string to `True` or `False`. It is particularly useful for constraints that are awkward for SMT, such as palindrome or balanced-structure checks.

**Declarative checker (SMT expression):**

```text
(and
  (str.contains s "@")
  (not
    (str.in_re s
      (re.++ (re.* re.allchar) (str.to_re "@")
             (re.* re.allchar) (str.to_re "@")
             (re.* re.allchar)))))
```

It denotes the set of strings satisfying a requirement. Multiple expressions can be conjoined and sent to an SMT solver. In the experiments, checker generation targets an SMT string expression, and the resulting constraints are evaluated through a solver interface; the evaluation uses CVC5 for ground truth/equivalence work and describes using Python's Z3 API for generated-checker validation.

The verifier also produces an **LLM-derived verification outcome (LVO)**:

- `UNSAT`, or
- `SAT + data`, meaning a candidate string that supposedly satisfies all requirements.

### 2.3 Final output

The public result is a verification outcome:

```text
SAT + <satisfying string>
UNSAT
UNKNOWN + best saved approximate result
```

More formally:

```text
verification outcome = SAT | UNSAT | UNKNOWN
```

- A confirmed SAT result includes LLM-generated string data as the witness.
- A confirmed UNSAT result is accepted only through a declarative checker.
- UNKNOWN means the budget was exhausted or the checker could not establish correctness. The system still reports its closest-to-sound saved guess: approximately SAT (`~SAT`, with the best candidate) or approximately UNSAT (`~UNSAT`). This fallback is **not a proof**.

## 3. System architecture

The complete pipeline has two components:

```text
Natural-language requirements
            |
            v
    +-------------------+
    | Checker generator |
    +-------------------+
            |
            | one Python and/or SMT checker per requirement
            v
    +------------------------+
    | Checker-based verifier | <---- original NL requirements
    +------------------------+
            |
            v
   SAT + data / UNSAT / UNKNOWN
```

The checker generator creates an executable interpretation of each requirement. The verifier separately asks an LLM to solve the overall problem. Keeping these roles separate creates a proposer-verifier pattern: one process proposes an answer and another checks it.

The system can also be viewed as a two-agent workflow:

- **Checker-generation agent:** translates natural language into validation logic.
- **Verification agent:** reasons over the complete requirement set and proposes a candidate or `UNSAT`.

The second agent is not allowed to validate itself; generated checkers mediate acceptance.

## 4. Methodology, stage 1: checker generation

### Step 1: split the requirements into batches

The requirements are divided into batches that are independently converted to checkers. The paper studies two settings:

- **BATCH:** two batches per requirement set, one holding all positive requirements and another holding all negated requirements.
- **IND:** each individual requirement becomes its own batch.

Batching fewer requirements together needs fewer LLM calls and can expose relationships between requirements. IND uses more calls but simplifies each translation problem. The experiments find that IND generally produces better SMT checkers, especially for smaller models.

### Step 2: prompt an LLM to convert each batch

The prompting differs by target language.

#### Python checker generation

The paper uses zero-shot code generation. The prompt contains:

- a Python function signature;
- a docstring containing the natural-language requirement.

This resembles HumanEval: the function contract describes the intended behavior, and the model fills in the body.

#### SMT checker generation

The prompt is one-shot. It contains:

- the current natural-language requirements;
- one example pair mapping natural-language requirements to SMT checker expressions;
- an instruction to produce exactly one SMT expression string for each requirement.

The example primarily teaches the expected representation and output format.

Both prompt types also use:

- a role description;
- chain-of-thought instructions;
- emotional-stimulus wording intended to improve compliance;
- structured-output parsing through LangChain.

### Step 3: evaluate each generated checker

Soundness is evaluated separately for each checker, even if several checkers were generated in one batch.

#### Syntactic soundness

A language-specific parser checks whether the artifact can be parsed or executed. Let `V` be the set of generated checkers, and let `P(v)` equal 1 when checker `v` parses successfully and 0 otherwise. Syntax accuracy is:

```text
Syntax Accuracy = number of syntactically valid checkers / total generated checkers
                = sum of P(v) for every v in V / |V|
```

This is intentionally all-or-nothing per checker because an unparseable checker cannot be used.

#### Semantic soundness by testing

For every requirement, the authors manually construct five satisfying strings and five violating strings. Let `Sv` be these ten samples for generated checker `v`, let `v_gt` be its ground-truth checker, and let `E(v, s)` be the checker's result. A checker counts as correct only if it agrees with ground truth on **all ten samples**:

```text
Testing Accuracy = checkers correct on all 10 associated samples
                   ----------------------------------------------
                         total generated checkers

Checker v is correct when E(v, s) = E(v_gt, s) for every s in Sv.
```

This is useful for both Python and SMT checkers, but it is not a proof: an incorrect checker can pass a finite test set.

#### Formal semantic soundness for SMT

For SMT checkers, equivalence to the manually written ground-truth constraint can be submitted to CVC5. Formal accuracy is:

```text
Formal Accuracy = generated SMT checkers proven equivalent to ground truth
                  ---------------------------------------------------------
                               total generated checkers
```

Only explicitly proven equivalence counts as correct; timeout and `unknown` do not. The paper does not claim an equivalent formal procedure for arbitrary Python functions.

### Step 4: repair failed checkers

If any checker in a batch is unsound, the system collects diagnostics, such as the identities of invalid checkers or parser failures, and returns them to the LLM for regeneration. The experiment permits at most **two checker-generation LLM calls**. Once all checkers pass the configured check, the batches are merged into the final checker set.

### Important nuance

The general method discusses both syntactic and optional semantic validation, but the RQ1 generation setup feeds parser-derived **syntactic** feedback during retries. The authors use ground-truth tests and formal equivalence primarily to measure checker quality. In a realistic deployment, ground-truth checkers are unavailable; therefore, generated checker semantics remain a central source of risk.

## 5. Methodology, stage 2: checker-based verification

### Step 1: ask the verifier LLM for an LVO

The verifier receives the entire natural-language requirement set. Its prompt asks it to:

1. analyze whether the constraints are logically consistent;
2. generate a realistic string satisfying every requirement if possible;
3. otherwise return `UNSAT`;
4. follow a structured output format.

On later iterations, the prompt can also include prior failed candidates and explanations of their violations.

### Step 2: choose the validation route

The LVO determines which checker can be used.

#### If the LLM returns `SAT + data`

The system runs the candidate through the individual checkers. Either checker family can reject a bad candidate:

- Python directly evaluates every predicate on the string.
- SMT adds the concrete string value as a constraint and checks consistency.

If all required checks pass, the candidate is returned as a confirmed SAT result.

#### If the LLM returns `UNSAT`

Only the declarative SMT route can validate the claim. Python has no candidate to execute and cannot search the infinite string space to prove nonexistence. The SMT solver checks the conjunction of the generated constraints:

```text
R1(s) AND R2(s) AND ... AND Rn(s)
```

If the solver establishes unsatisfiability, the system returns confirmed `UNSAT`.

### Step 3: handle correct, incorrect, and unknown validation

- **Correct:** immediately return the current LVO.
- **Incorrect:** score and save the LVO, gather feedback, check the remaining budget, and retry if possible.
- **Unknown:** do not enter the feedback loop because the checker has not established that the LVO is wrong. Return `UNKNOWN` with the best saved approximation.

### Step 4: score imperfect LVOs

For a failed `SAT + data` proposal, quality is the proportion of individual requirements satisfied:

```text
quality(s) = number of requirements satisfied by s / total requirements
```

For a failed `UNSAT` proposal that the declarative checker finds satisfiable, the system assigns a fixed quality value.

The authors intentionally do not return an SMT-produced model as the final satisfying data. Solver-generated strings may be unrealistic, and the generated SMT checker may itself be wrong. The LLM remains responsible for producing human-plausible data.

### Step 5: use one of three feedback levels

- **+V — validation only:** tell the LLM that the previous answer was invalid and ask it to try again. Previous values are not supplied.
- **+VF — validation plus failed values:** include prior LVOs as counterexamples, but do not explain their failures.
- **+VFE — validation, failed values, and explanations:** include counterexamples and identify the exact natural-language requirements each candidate violated.

The difference matters. A raw counterexample can confuse the model because it shows what failed without saying why. Explanatory feedback gives a local repair signal.

### Step 6: enforce a budget and degrade gracefully

The verifier gets at most **five LLM calls** in the experiments. If no candidate is confirmed within the budget:

1. If saved `UNSAT` proposals outnumber saved `SAT + data` proposals, choose `~UNSAT`.
2. Otherwise, choose the SAT candidate with the highest satisfied-requirement ratio and label it `~SAT`.
3. Return the formal top-level outcome `UNKNOWN` alongside this best saved LVO.

This is a pragmatic fallback for interactive use, not a correctness guarantee.

### Verifier pseudocode

```text
input: NL requirements R, generated checkers C, budget B
saved = []

for attempt in 1..B:
    lvo = LLM_propose(R, feedback_from(saved))
    verdict = validate(lvo, C)

    if verdict == CORRECT:
        return lvo                         # UNSAT or SAT + data

    if verdict == UNKNOWN:
        return UNKNOWN, best(saved)

    quality = score(lvo, C)
    saved.append(lvo, quality, violations)

return UNKNOWN, best(saved)
```

## 6. Worked example

Consider these requirements:

```text
R1: exactly one "@"
R2: does not end in "."
R3: at least one "." after "@"
```

### Case A: all positive requirements

The verifier proposes `ab@cd.com`.

```text
R1("ab@cd.com") = true
R2("ab@cd.com") = true
R3("ab@cd.com") = true
```

All checkers accept, so the result is `SAT + "ab@cd.com"`.

### Case B: `R1 AND NOT R2 AND NOT R3`

- `NOT R2` means the string **must end with `.`**.
- `NOT R3` means there is **no `.` after `@`**.
- Because `R1` requires an `@`, a final `.` necessarily lies after that `@`.

The last two conditions therefore contradict each other. An SMT checker can establish that their conjunction has no model, so the result is `UNSAT`.

### Case C: failed proposal and repair

Suppose the verifier proposes `ab@cd.` for the all-positive case. It satisfies R1 and R3 but violates R2. Under +VFE, the next prompt effectively says:

```text
Counterexample: "ab@cd."
Violation: R2, because the value ends with a period.
```

The LLM can locally repair the suffix and propose `ab@cd.com` on the next iteration.

## 7. Experimental methodology

### Models

The paper evaluates four LLMs:

- GPT-4o
- GPT-4o-mini
- DeepSeek-V3
- Llama 3.1 8B

Temperatures are set to `0` for the open-source models and `0.01` for GPT models to reduce variation. A temperature of `0.1` is used where controlled retry variation is required, such as validation-only retries.

### Dataset

The authors use 12 string categories drawn from common programming exercises:

1. Email
2. Name
3. Password
4. URL
5. Date
6. IBAN number
7. ISBN number
8. Arithmetic expression
9. Palindrome
10. Parentheses sequence
11. DNA sequence
12. File path

They generate **340 requirement sets** by combining positive and negated requirements using equivalence partitioning. These include regular-language problems and context-free-style problems that may require computational power up to pushdown automata.

For ground-truth labels, the authors manually translate requirements into SMT-LIB2 and run CVC5 with a five-second timeout:

- CVC5 initially reports 230 SAT;
- 54 UNSAT;
- 56 UNKNOWN.

Manual inspection of the 56 unknown cases finds 53 SAT and 3 UNSAT, producing final labels of:

- **283 SAT**
- **57 UNSAT**

The dataset is therefore imbalanced, which is why the paper reports SAT data-generation quality separately from UNSAT classification quality.

### Research questions

- **RQ1:** How sound are LLM-generated Python and SMT checkers?
- **RQ2:** With ground-truth checkers, how do checker type and feedback detail affect verifier output?
- **RQ3:** What happens end to end when checkers are themselves LLM-generated?

### Metrics

#### Generation Success Rate (GSR)

For the satisfiable subset `D_sat`, GSR is the fraction for which the approach generates a string accepted by the ground-truth checker:

```text
GSR = satisfiable requirement sets given a valid generated string
      ------------------------------------------------------------
                total satisfiable requirement sets
```

GSR does not measure UNSAT detection; it measures successful witness generation for truly satisfiable inputs.

#### UNSAT precision, recall, and F1

Let `D_unsat` be the true UNSAT set and `S_unsat` the cases predicted UNSAT:

```text
Precision = correctly predicted UNSAT cases / all predicted UNSAT cases

Recall    = correctly predicted UNSAT cases / all truly UNSAT cases

F1        = 2 * Precision * Recall / (Precision + Recall)
```

- Precision asks: when the system says UNSAT, how often is it right?
- Recall asks: of all truly UNSAT cases, how many does it catch?
- F1 balances the two.

## 8. Results and how to interpret them

### RQ1: checker generation

For Python checkers:

- All four LLMs achieve 100% syntax accuracy in both batching configurations.
- GPT-4o, GPT-4o-mini, and DeepSeek-V3 achieve 100% testing accuracy.
- Llama 3.1 8B is still near perfect, at roughly 98% in IND and 100% in BATCH.

For SMT checkers:

- Model size/capability matters much more.
- GPT-4o and DeepSeek-V3 exceed 85% syntax accuracy and 75% testing accuracy in IND.
- Llama 3.1 8B falls below 20% syntax and testing accuracy in IND.
- Testing accuracy is close to formal accuracy, suggesting that many checkers passing the ten samples are also formally equivalent to ground truth in this dataset.
- IND consistently beats BATCH for SMT generation. The gain exceeds 10 percentage points for GPT-4o-mini but is only around 3 points for GPT-4o, suggesting larger models handle multi-requirement prompts more easily.

**Interpretation:** LLMs are already very good at translating local string rules into Python. SMT syntax and semantics are substantially harder. Decomposition reduces that difficulty.

### RQ2: verification with ground-truth checkers

The direct, single-call baseline has strongly model-dependent GSR:

| Verifier LLM | Direct GSR | Direct UNSAT F1 |
|---|---:|---:|
| GPT-4o-mini | 66.43% | 59.83% |
| GPT-4o | 78.45% | 63.64% |
| DeepSeek-V3 | 72.08% | 58.49% |
| Llama 3.1 8B | 25.80% | 34.29% |

Adding validation generally improves string generation. Examples:

- GPT-4o rises from 78.45% direct GSR to 91.87% with Python +V.
- Llama 3.1 8B rises from 25.80% to 55.48% with SMT +V, more than doubling.
- The highest observed GSR is 92.23%, reached by GPT-4o with Hybrid +V or +VFE.

Counterexamples without explanations (+VF) do not always improve GSR and can reduce it. With Llama 3.1 8B and SMT, GSR drops from 55.48% under +V to 48.76% under +VF. Adding explanations (+VFE) improves GSR over both +V and +VF in 7 of 12 checker/model comparisons.

Python alone does not consistently improve UNSAT F1 because it cannot validate `UNSAT`. SMT does, and Hybrid combines SMT's UNSAT reasoning with Python's stronger candidate checking. The most dramatic example is Llama 3.1 8B:

```text
Direct UNSAT F1:       34.29%
Hybrid +VFE UNSAT F1: 87.10%
```

With ground-truth checkers, Hybrid +VFE gives:

- GSR between 57.24% and 92.23%; and
- UNSAT F1 between 82.59% and 94.64% across the four models.

The paper's summary says Hybrid +VFE is the strongest overall configuration: it has the top GSR for three of four LLMs and the top F1 range across all models.

### RQ3: end-to-end system with generated checkers

RQ2 is an upper bound because its checkers are correct by construction. RQ3 instead combines:

- IND-generated checkers from each LLM; and
- the Hybrid +VFE verifier configuration.

Most generated-checker configurations outperform direct generation. Important findings are:

- DeepSeek-V3-generated checkers paired with GPT-4o or DeepSeek-V3 verifiers reach more than 95% of the ground-truth-checker GSR upper bound.
- The best end-to-end F1 reaches about 88% of its ground-truth-checker upper bound, using a GPT-4o-mini verifier with DeepSeek-V3-generated checkers.
- Every verifier has an F1 ratio above 60% in the reported best configurations.
- Better checker generators generally produce better end-to-end results. DeepSeek-V3-generated checkers give the best GSR for three of four verifier models; GPT-4o-generated checkers give the best F1 for three of four.
- Even poor Llama-generated SMT checkers can sometimes improve strong GPT-4o and DeepSeek-V3 verifiers, which indicates some robustness to checker imperfections.
- The main exceptions are combinations where Llama-generated checkers are paired with the smaller GPT-4o-mini or Llama verifier.

**Interpretation:** checker generation quality, especially SMT quality, is now the bottleneck. The feedback architecture works, but it cannot recover perfectly from an incorrect validator.

## 9. What the paper contributes

1. It removes the requirement that a user manually formalize the natural-language input before satisfiability checking.
2. It treats SAT and UNSAT as first-class outcomes. Many test-data methods assume satisfiability and only generate values.
3. It generates realistic LLM witnesses for SAT while reserving formal machinery for validation.
4. It combines complementary checkers:
   - Python is expressive and reliable for candidate validation.
   - SMT can validate candidates and establish UNSAT, when the encoding and solver succeed.
5. It turns checker failures into iterative, requirement-specific feedback.
6. It decomposes checker generation per requirement, improving difficult formal translation.
7. It provides a bounded fallback rather than looping indefinitely.

## 10. Assumptions, limitations, and failure modes

### The key unsoundness failure

If the proposer and generated checker are both wrong in a compatible way, they can agree on a false result. Validation only helps when the validator is independent enough and correct enough to detect the proposal's error.

For example, if an LLM misreads "exactly one `@`" as "at least one `@`" in both its candidate reasoning and its generated checker, a string with two `@` symbols can be falsely accepted.

The authors explicitly identify this as a critical failure mode and suggest redundant or cross-validated checkers as future safeguards.

### `UNKNOWN` is not SAT or UNSAT

The `~SAT` and `~UNSAT` outputs are best-effort guesses nested under an `UNKNOWN` outcome. They should not be treated as formally verified results.

### SMT limitations remain

Declarative solvers may time out or return `unknown` on recursion, universal quantification, or complex string structure. The paper mentions balanced arithmetic-formula parentheses and universal-quantifier limitations as examples.

### Python cannot establish nonexistence

An imperative predicate can reject any tested candidate, but repeated rejection never proves that no possible string exists. UNSAT validation therefore depends on SMT.

### Finite tests can miss checker bugs

Testing accuracy uses ten manually designed samples per requirement. Passing all ten is evidence, not proof. Formal accuracy is stronger but is available only for the SMT artifacts in this evaluation and can itself encounter solver timeout or `unknown`.

### Ground truth required manual work

The dataset labels, reference SMT constraints, and checker test samples were manually produced and cross-checked. Mistakes or author bias could influence the evaluation.

### Dataset limitations

- The 340 cases cover 12 programming-exercise categories, not industry-scale requirements documents.
- The dataset is imbalanced: 283 SAT versus 57 UNSAT.
- Base requirements may have appeared in model training data, although unusual combinations and negations are less likely to have appeared.
- Requirements are about a single string variable and are relatively controlled. Generalization to multiple interacting variables, domain rules, temporal behavior, or ambiguous prose is not established.

### Prompting and implementation choices

The observed results depend on the chosen prompts, retry budgets, temperatures, structured-output layer, selected solvers, and the four model versions. They should not be interpreted as timeless properties of each model family.

## 11. How to reproduce the study conceptually

1. Define natural-language rules for a string category.
2. Produce positive and negated combinations of those rules.
3. Manually create trusted reference constraints and label each combination SAT or UNSAT.
4. For each individual rule, create five valid and five invalid strings.
5. Prompt an LLM to generate Python and SMT checkers under BATCH and IND configurations.
6. Parse each checker and retry once with syntax diagnostics if required.
7. Measure syntax, test, and SMT formal-equivalence accuracy.
8. Prompt the verifier LLM directly to obtain the baseline LVO.
9. Repeat verification with Python, SMT, and Hybrid checkers under +V, +VF, and +VFE, up to five calls.
10. Measure SAT witness GSR and UNSAT precision/recall/F1.
11. First use ground-truth checkers to estimate the verifier's upper bound (RQ2).
12. Replace them with LLM-generated IND checkers to measure realistic end-to-end performance (RQ3).

The accompanying artifact cited by the paper is reference [36], DOI `10.5281/zenodo.15679384`.

## 12. A compact mental model

Remember the paper as four verbs:

1. **Translate:** Convert every natural-language rule into Python and/or SMT.
2. **Propose:** Ask an LLM for `UNSAT` or a realistic satisfying string.
3. **Check:** Use SMT for UNSAT; use Python plus SMT for candidate strings.
4. **Repair:** Feed failed values and requirement-level explanations back to the proposer within a fixed budget.

The central lesson is not simply "LLMs can solve constraints." It is:

> LLM reasoning becomes substantially more useful when its outputs are forced through independently executable interpretations of the original requirements, and when validation failures are converted into precise repair feedback.

The remaining challenge is that those executable interpretations are also generated by LLMs. Python checker generation is already highly reliable on this benchmark, while SMT checker generation is the major obstacle to stronger end-to-end guarantees.

## 13. Glossary

- **Constraint:** A condition that a value must satisfy.
- **Conjunction:** Logical AND across all requirements.
- **SAT:** At least one value satisfies all constraints.
- **UNSAT:** No value satisfies all constraints.
- **UNKNOWN:** The procedure could not establish SAT or UNSAT within its capabilities or budget.
- **Witness / proof of satisfiability:** A concrete value satisfying every constraint.
- **LVO:** LLM-derived verification outcome, either `UNSAT` or `SAT + data`.
- **Imperative checker:** Executable code, here Python, that checks a concrete value.
- **Declarative checker:** A logical specification, here SMT, describing acceptable values.
- **SMT:** Satisfiability Modulo Theories, a framework for deciding logical formulas over domains such as strings and integers.
- **CVC5 / Z3:** SMT solvers.
- **Syntax accuracy:** Fraction of generated checkers that parse correctly.
- **Testing accuracy:** Fraction of checkers agreeing with ground truth on every designed test sample.
- **Formal accuracy:** Fraction of SMT checkers whose equivalence to ground truth is formally proven.
- **GSR:** Fraction of genuinely satisfiable cases for which a valid string is generated.
- **BATCH:** Generate checkers for multiple related requirements together.
- **IND:** Generate one checker from one requirement at a time.
- **+V:** Retry after a failed validation.
- **+VF:** Retry with failed prior values as counterexamples.
- **+VFE:** Retry with failed values and explanations of requirement violations.
