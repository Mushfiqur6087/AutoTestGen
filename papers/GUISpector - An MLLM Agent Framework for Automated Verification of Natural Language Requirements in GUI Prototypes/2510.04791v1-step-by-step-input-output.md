# GUISpector: Step-by-Step Input and Output Guide

## Scope and evidence labels

This guide traces the pipeline in [2510.04791v1.pdf](2510.04791v1.pdf).

- Architecture, dataset sizes, actions, outputs, and technologies are directly reported by the paper.
- The paper describes three zero-shot prompts but does not print their complete text.
- The Cleaning Booking example below is a **pedagogical reconstruction** based on the paper's statement that editing may require first configuring an appointment.

## Running example

```text
Application: Cleaning Booking
Starting URL: http://local-app/

Requirement: A user can edit an existing cleaning appointment.

AC1: An appointment can be created.
AC2: The appointment can be opened for editing.
AC3: Saving changes updates the displayed appointment.

Test data:
customer = "Amina Rahman"
date = "2026-09-25"
service = "Deep cleaning"
updated_service = "Standard cleaning"
```

The requirement wording, criteria, URL, and values are illustrative. They model the prerequisite flow described by the authors but are not quoted dataset records.

## Prompt availability

| LLM step | Information provided by the paper | Full prompt printed? |
|---|---|---:|
| NL requirement processing | Zero-shot LLM extracts structured description and criteria and may infer missing details | No |
| MLLM GUI verification | Zero-shot instructions enforce autonomy, minimal actions, use of test data, criterion-level evaluation, evidence, and structured JSON | No |
| Programming-agent repair loop | Zero-shot instructions tell an external agent to retrieve failures, implement changes, and rerun verification | No |

The paper never identifies text as a specific API system-role message. Prompt blocks below are illustrative reconstructions.

## Step 1 - Create the verification setup

### Who performs this step

Human user and GUISpector's web interface.

### Input

The application URL, natural-language requirement, and appointment test data shown above.

### How this step is done, simply

1. The user selects or registers the GUI application.
2. The user pastes requirements.
3. The user adds values the GUI agent may need to type.
4. Normal application code stores the setup in MySQL.

### Prompt used

None. This is data entry and persistence.

### Output

```yaml
verification_setup:
  application: Cleaning Booking
  start_url: http://local-app/
  requirements: [raw_requirement_text]
  test_data:
    customer: Amina Rahman
    date: 2026-09-25
    service: Deep cleaning
    updated_service: Standard cleaning
```

## Step 2 - Structure the natural-language requirement

### Who performs this step

Zero-shot LLM plus normal controller code.

### Input

```text
A user can edit an existing cleaning appointment.
```

### How this step is done, simply

1. The controller inserts the raw requirement into a prompt template.
2. The LLM extracts a description and individual acceptance criteria.
3. It may infer missing details from context.
4. A response parser stores the structured result.

### Prompt used

The paper describes the task but does not print the prompt. Illustrative reconstruction:

```text
Convert the natural-language GUI requirement into a structured requirement.
Return its description and independently verifiable acceptance criteria.
Infer missing details only when the context supports them.

Requirement: {requirement}
```

### Output

```yaml
requirement:
  description: A user can edit an existing cleaning appointment.
  acceptance_criteria:
    - AC1: An appointment can be created.
    - AC2: The appointment can be opened for editing.
    - AC3: Saving changes updates the displayed appointment.
```

## Step 3 - Schedule an isolated verification run

### Who performs this step

Celery, Redis, the display resource manager, and environment-management code.

### Input

The structured requirement, target application, and a request to start verification.

### How this step is done, simply

1. Celery queues the background job.
2. Redis allocates an available Xfce desktop running on Xvfb.
3. Preparation code resets the application to a clean state.
4. The controller opens the starting URL.
5. A screenshot is captured.

### Prompt used

None. This is infrastructure orchestration.

### Output

```yaml
run_id: example-run-1
display: allocated_virtual_display
initial_state: clean
initial_screenshot: GUI_1
```

### Failure or alternate branch

If no display is available, the job waits or fails operationally; the paper does not specify a detailed failure policy.

## Step 4 - Initialize the MLLM verifier

### Who performs this step

GUISpector controller and a pretrained computer-use MLLM.

### Input

```yaml
requirement: structured requirement
acceptance_criteria: [AC1, AC2, AC3]
test_data: appointment values
screenshot: GUI_1
```

### How this step is done, simply

1. The controller fills a zero-shot prompt.
2. It attaches the current screenshot.
3. The MLLM receives the prompt, requirement data, and image.
4. The prompt asks the model to act autonomously and gather evidence with few actions.

### Prompt used

The full prompt is not printed. The paper-described constraints can be represented by this illustrative reconstruction:

```text
Autonomously verify every acceptance criterion in the supplied GUI.
Start at the given URL, use the provided test data, and take only necessary actions.
Judge each criterion independently and support the judgment with concrete evidence.
Return a structured JSON summary when verification is complete.
```

### Output

An initialized agent state ready to choose its first action.

## Step 5 - Reason about the next action

### Who performs this step

The MLLM.

### Input

Current screenshot `GUI_t`, the requirement, criteria, test data, and accumulated trajectory.

### How this step is done, simply

The model visually inspects the page, decides which unverified criterion to pursue, and identifies the next interaction most likely to collect evidence.

### Prompt used

The same zero-shot verification prompt remains in context. The paper does not provide a separate per-action prompt.

### Output

Illustrative first decision:

```yaml
reasoning_t: No appointment exists, so create one before testing editing.
action_t:
  type: click
  x: 742
  y: 318
  target_description: New appointment button
```

Coordinates and reasoning are reconstructed for teaching.

## Step 6 - Execute the GUI action

### Who performs this step

GUISpector environment code and `xdotool`.

### Input

The structured action produced by the MLLM.

### How this step is done, simply

The controller converts the action into an operating-system interaction. A click action becomes an `xdotool` pointer movement and click; a type action becomes keyboard input.

### Prompt used

None. The system executes the action deterministically.

### Output

The GUI changes state and GUISpector captures `GUI_(t+1)`.

## Step 7 - Repeat the perception-action loop

### Who performs this step

MLLM, controller, GUI application, screenshot capture, and xdotool.

### Input

New screenshot plus all prior trajectory context.

### How this step is done, simply

Steps 5 and 6 repeat. An illustrative trajectory is:

```text
GUI_1 -> click New Appointment
GUI_2 -> type customer, date, and service
GUI_3 -> click Save
GUI_4 -> open the saved appointment
GUI_5 -> click Edit
GUI_6 -> replace service value
GUI_7 -> click Save
GUI_8 -> inspect displayed appointment
```

### Prompt used

The same paper-described verification prompt; no full text is published.

### Output

```text
(GUI_1, reasoning_1, action_1, ..., GUI_8, reasoning_8, action_8)
```

### Failure or alternate branch

The agent may take an incorrect action, fail to find a control, or collect insufficient evidence. The paper does not detail retry or maximum-step logic.

## Step 8 - Judge every acceptance criterion

### Who performs this step

The MLLM.

### Input

The full trajectory and visible evidence.

### How this step is done, simply

The model reviews what happened and assigns a met/unmet judgment to each criterion. It must justify every judgment using concrete observations from the trajectory.

### Prompt used

The zero-shot verification prompt requires criterion-level evaluation, evidence, and structured JSON; the exact output schema is not printed.

### Output

Illustrative failure output:

```json
{
  "acceptance_criteria": [
    {"id": "AC1", "status": "met", "evidence": "Appointment appeared in the list."},
    {"id": "AC2", "status": "met", "evidence": "Edit form opened for the saved appointment."},
    {"id": "AC3", "status": "unmet", "evidence": "After Save, the old service remained visible."}
  ],
  "summary": "Editing opens, but the changed service is not persisted or displayed."
}
```

## Step 9 - Derive requirement status

### Who performs this step

Normal program code.

### Input

Criterion states: `[met, met, unmet]`.

### How this step is done, simply

```python
if all(criteria_met):
    requirement_status = "met"
elif not any(criteria_met):
    requirement_status = "unmet"
else:
    requirement_status = "partially met"
```

### Prompt used

None.

### Output

```yaml
requirement_status: partially_met
```

## Step 10 - Show evidence to a human

### Who performs this step

GUISpector UI and human user.

### Input

Status, criterion results, screenshots, actions, reasoning, and summary.

### How this step is done, simply

The web interface updates the requirements-status view and trajectory view. The user can inspect why a criterion failed and which screenshots support the conclusion.

### Prompt used

None.

### Output

A human-inspectable report and actionable feedback.

## Step 11 - Optionally send the failure to a coding agent

### Who performs this step

External LLM programming agent, MCP server, and AI-enabled IDE.

### Input

```yaml
requirement_status: partially_met
failed_criterion: AC3
feedback: The edited service is not persisted or displayed after Save.
```

### How this step is done, simply

1. The programming agent queries GUISpector through MCP.
2. It retrieves violated or unverified requirements.
3. It inspects the codebase and implements a correction.
4. It calls GUISpector to rerun verification.
5. It repeats until the requirement is met, then continues to the next requirement.

### Prompt used

The paper says a zero-shot prompt instructs the agent to follow this loop, but it does not print it. Illustrative reconstruction:

```text
Retrieve failed or unverified requirements from GUISpector.
For each requirement, use its acceptance-criterion feedback to implement a fix.
Rerun GUISpector after the change. Continue until the requirement is met,
then proceed to the next requirement.
```

### Output

Modified GUI code and a request for another verification run.

## Step 12 - Rerun and terminate

### Who performs this step

The same controller, MLLM loop, and optionally the programming agent.

### Input

Revised GUI application plus the unchanged requirement and test data.

### How this step is done, simply

GUISpector starts from a clean environment and executes the verification trajectory again. If all criteria are met, the requirement becomes met. Otherwise, new feedback begins another repair cycle.

### Output

Success example:

```yaml
acceptance_criteria:
  AC1: met
  AC2: met
  AC3: met
requirement_status: met
```

### Failure or alternate branch

The paper does not define a convergence guarantee, retry limit, or fallback state for the complete coding-agent loop.

## Component contract table

| Component | Actor | Input | Transformation | Output |
|---|---|---|---|---|
| Setup UI | Human + web app | App, requirements, test data | Store verification setup | Persisted setup |
| NL processing | LLM | Raw requirement | Extract/infer structured fields | Description + criteria |
| Scheduler | Celery + Redis | Run request | Queue and allocate display | Isolated run |
| Environment | Xfce/Xvfb | App and URL | Prepare clean GUI | Initial screenshot |
| MLLM verifier | Computer-use MLLM | Requirement, criteria, data, screenshot | Reason and select action | Reasoning + action |
| Action executor | xdotool | Action and parameters | Interact with GUI | New GUI state |
| Evidence summarizer | MLLM | Full trajectory | Judge criteria and cite evidence | Structured JSON |
| Status derivation | Program code | Criterion labels | Apply all/none/mixed rule | Met/partial/unmet |
| Human interface | Web app | Results and trajectory | Render inspection views | Human-readable evidence |
| MCP integration | MCP server | Queries and run commands | Bridge external agent | Requirements and feedback |
| Repair agent | Programming LLM | Code + failure feedback | Implement change | Revised GUI |

## Final mental model

```text
Human gives requirement and data
    -> LLM structures acceptance criteria
    -> MLLM sees screenshot and acts
    -> GUI returns new screenshot
    -> MLLM accumulates evidence
    -> JSON criterion judgments
    -> status and actionable feedback
    -> human review or coding-agent repair
    -> clean rerun
```
