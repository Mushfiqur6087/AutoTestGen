# Learning Guide: GUISpector

## Paper at a glance

- **Title:** *GUISpector: An MLLM Agent Framework for Automated Verification of Natural Language Requirements in GUI Prototypes*
- **Authors:** Kristian Kolthoff, Felix Kretzer, Simone Paolo Ponzetto, Alexander Maedche, and Christian Bartelt
- **Version:** arXiv:2510.04791v1, 6 October 2025
- **Source:** [2510.04791v1.pdf](2510.04791v1.pdf)
- **Task:** Determine whether an interactive GUI satisfies natural-language requirements and their acceptance criteria.
- **Core idea:** Give a computer-use multimodal LLM a requirement, test data, and screenshots; let it operate the GUI, collect evidence, and return structured judgments and actionable feedback.

GUISpector does not train a new model. It orchestrates pretrained LLMs and a pretrained multimodal computer-use model at inference time.

## 1. Problem and motivation

GUI prototypes are used early in requirements elicitation, but manually checking that a prototype implements every requirement is slow. Traditional GUI test scripts are brittle, random exploration may miss important states, and approaches based only on textual GUI trees ignore visual and dynamic behavior.

GUISpector addresses three connected needs:

1. Interpret unstructured natural-language requirements.
2. Autonomously interact with the actual GUI to gather visual evidence.
3. Turn verification failures into feedback that a developer or coding agent can use.

The system supports both a human-supervised workflow and a closed implementation-verification loop driven by an external programming agent.

## 2. Inputs, intermediate artifacts, and outputs

### External inputs

- Target GUI application and starting URL.
- Natural-language requirements.
- Acceptance criteria, extracted or inferred from each requirement.
- Test input data such as usernames, promo codes, or payment details.
- Current GUI screenshot/state.
- In automatic mode, an external programming agent connected through MCP.

### Intermediate artifacts

- Structured requirement records containing descriptions and acceptance criteria.
- MLLM reasoning at each interaction step.
- GUI actions such as click, double-click, scroll, and type, including coordinates or text parameters.
- Successive screenshots after actions.
- A trajectory:

```text
GUI state 1, reasoning 1, action 1, ..., GUI state n, reasoning n, action n
```

- Evidence attached to individual acceptance-criterion judgments.
- Requirement status: met, partially met, or unmet.

### Final outputs

- Structured JSON summary for each verification run.
- Met/unmet result and explanation for every acceptance criterion.
- Derived overall requirement state.
- Actionable feedback for violated or partially satisfied requirements.
- Human-readable trajectory views.
- In automatic mode, feedback returned through MCP to an LLM programming agent.

## 3. Architecture

Figure 1 divides GUISpector into three components.

### A. Human-in-the-verification-loop

The user selects an application, supplies requirements and test data, monitors statuses, and inspects trajectory details. A zero-shot LLM converts unstructured requirements into structured descriptions and acceptance criteria. The interface exposes rationales and evidence rather than only a pass/fail label.

### B. MLLM GUI-agent verification loop

The computer-use agent receives a requirement, its criteria, test data, and a screenshot. It reasons about the next useful action, executes that action, receives a new screenshot, and repeats until it can judge each criterion. The framework prepares a clean GUI environment before the run and cleans it afterward.

### C. Agentic implementation-verification loop

An external coding agent connects through a Model Context Protocol server. It retrieves unverified or failed requirements, changes the GUI code, invokes GUISpector again, reads the returned explanations, and repeats until the requirement is met before moving to the next item.

## 4. Detailed methodology

### Step 1: capture the verification setup

The human supplies the application, free-form requirements, and test values. This establishes both what should be checked and which concrete values the agent may need while interacting.

### Step 2: structure natural-language requirements

A zero-shot LLM extracts a description and individual acceptance criteria. It may infer missing details from context. The paper does not print this prompt or distinguish system and user API messages.

### Step 3: allocate an isolated GUI environment

GUISpector assigns a virtual display to the run. It uses Xfce desktops on Xvfb virtual displays, with a Redis-based display resource manager. Cleanup before and after runs avoids state contamination.

### Step 4: initialize the MLLM agent

The agent receives:

- the requirement;
- all acceptance criteria;
- test data;
- the current screenshot;
- zero-shot instructions to act autonomously, minimize actions, use supplied data, judge each criterion separately, cite evidence, and return structured JSON.

The paper describes these prompt constraints but does not print the complete prompt.

### Step 5: reason and act

At time `t`, the model inspects screenshot `GUI_t`, creates reasoning `r_t`, and predicts action `a_t`. The action may contain a verb and parameters, for example a click with `(x, y)` coordinates or a type action with text.

GUISpector executes the action through `xdotool`, causing the application to produce `GUI_(t+1)`. That screenshot returns to the agent, closing the loop.

### Step 6: terminate with evidence

When enough evidence has been collected, the MLLM returns JSON containing the status, explanation, and evidence for each acceptance criterion. The overall requirement state is based on those criterion-level results.

### Step 7: expose results

Human users can inspect requirement status, screenshots, actions, reasoning, and evidence. Failures are written as actionable natural-language summaries.

### Step 8: optionally repair through MCP

In automatic mode, a programming agent queries GUISpector for failed items, implements changes in an AI-enabled IDE, and reruns verification. A zero-shot prompt instructs the programming agent to follow this loop, but the paper does not publish the full prompt.

## 5. Training-time versus inference-time behavior

### Training time

The paper reports no fine-tuning or additional model training. The evaluated computer-use model is OpenAI CUA. Other LLM tasks can use OpenAI GPT, Google Gemini, or Anthropic Claude Sonnet.

### Inference time

All core work happens during inference:

- requirement structuring;
- multimodal reasoning over screenshots;
- action prediction;
- criterion classification and evidence generation;
- coding-agent repair decisions.

## 6. Worked example

The paper mentions that some Cleaning Booking requirements require configuring an appointment before editing it. It does not print the exact requirement. The following is a pedagogical reconstruction consistent with that example.

```text
Requirement: A user can edit an existing cleaning appointment.

AC1: An appointment can be created.
AC2: The appointment can be opened for editing.
AC3: Saving changes updates the displayed appointment.
```

The user supplies appointment details as test data. The agent may:

1. Fill the booking form and create an appointment.
2. Locate the appointment in a list.
3. Open its edit control.
4. Change a field and save.
5. Inspect the updated display.

If AC1 and AC2 succeed but the edited value is not displayed, the output would mark AC3 unmet and derive the overall requirement as partially met. The feedback might identify that the save action does not persist or refresh the changed field. This trace is illustrative, not an experiment log printed by the paper.

## 7. Implementation

- **Backend:** Django
- **Frontend:** HTML, CSS, and JavaScript
- **Database:** MySQL
- **Background jobs:** Celery
- **Coordination and display allocation:** Redis
- **GUI environments:** Xfce on Xvfb
- **Interaction execution:** xdotool
- **External-agent integration:** MCP server
- **Evaluated verifier model:** OpenAI CUA

Parallel Celery workers and multiple virtual displays allow independent verification runs to execute simultaneously.

## 8. Experimental setup

### Dataset construction

Because an appropriate dataset did not exist, the authors created one with Codex:

- Five applications: Park-and-Pay, Budget Tracker, Recipe Generator, Fitness Quests, and Cleaning Booking.
- 30 functional requirements per application.
- Three acceptance criteria per requirement.
- 150 requirements total.
- 450 distinct acceptance criteria.
- Each app is a single local-state HTML file without external CDNs or APIs.

The target per-app requirement distribution was 18 met, six unmet, and six partially met.

### Gold standard

Two authors independently labeled all 450 criteria as met or unmet. Requirement labels were derived as follows:

```text
All criteria met     -> requirement met
All criteria unmet   -> requirement unmet
Mixed criterion state -> requirement partially met
```

Across 150 requirements, three raters - the LLM specification and two annotators - achieved ordinal Krippendorff's alpha of 0.929 with a 95% confidence interval from 0.880 to 0.966. Eight of 150 requirement-level disagreements occurred between the LLM and humans.

At criterion level, the two humans achieved Cohen's kappa of 0.921 and 96.7% agreement: 435 of 450 criteria. Per-app kappa ranged from 0.841 to 0.972.

### Evaluation procedure

Each application was analyzed in a single evaluation run. Requirement classification used three classes: met, partially met, and unmet. Acceptance-criterion classification used two: met and unmet. The paper reports precision, recall, and F1 for every class.

## 9. Metrics

```text
Precision = correct predictions of a class / all predictions of that class
Recall    = correct predictions of a class / all true examples of that class
F1        = harmonic mean of precision and recall
```

The paper also records per-requirement steps, elapsed seconds, input/output tokens, and estimated cost.

## 10. Results

Average F1 scores across five apps were:

| Level | Class | Average F1 |
|---|---|---:|
| Requirement | Met | 0.905 |
| Requirement | Unmet | 0.878 |
| Requirement | Partially met | 0.631 |
| Acceptance criterion | Met | 0.940 |
| Acceptance criterion | Unmet | 0.870 |

The method is strongest at criterion-level met detection and weakest on partially met requirements. The authors attribute the latter to semantic boundary ambiguity: a mixed state is harder to distinguish cleanly from overall success or failure.

Average resource usage per requirement was:

| Measure | Mean | Standard deviation |
|---|---:|---:|
| Steps | 24.4 | 5.8 |
| Time | 317.6 seconds | 68.8 |
| Input tokens | 221.7k | 54.3k |
| Output tokens | 2.269k | 0.364k |
| Estimated cost | $0.665 | $0.163 |

Input tokens dominate cost because screenshots and repeated context are supplied throughout the trajectory. App 5 needed the most steps on average, 34.2, while App 3 needed 19.5. The paper notes that runs may be slower than human testing in some cases, but parallel execution can offset wall-clock cost.

## 11. Main contributions

1. A multimodal agent that verifies natural-language requirements directly against interactive GUIs.
2. Criterion-level evidence and actionable natural-language failure explanations.
3. A human-facing interface for monitoring and trajectory inspection.
4. An MCP interface for closed-loop repair by coding agents.
5. A new dataset of five apps, 150 requirements, and 450 acceptance criteria.

## 12. Limitations and risks

- The study covers five generated, single-file applications rather than large production systems.
- Codex generated both specifications and apps, which may shape task regularity.
- The exact prompts are not printed in the paper.
- Partial satisfaction is considerably harder than clear met/unmet cases.
- Average runtime is over five minutes per requirement.
- Input-token consumption and cost are high.
- MLLM reasoning and visual grounding can still make incorrect observations or actions.
- The paper evaluates recognition, not whether the closed coding-agent loop always converges to a correct implementation.
- One human annotator had prior exposure to the specification, although both labeled independently.

## 13. Reproduction outline

1. Obtain the code, dataset, prompts, and prototypes from the repository cited as reference [1].
2. Deploy the Django, MySQL, Redis, and Celery stack.
3. Configure isolated Xfce/Xvfb displays and xdotool.
4. Load the five apps, 150 requirements, 450 criteria, and test data.
5. Configure a computer-use MLLM.
6. Run criterion-level verification from clean state.
7. Save reasoning, action, screenshot, and JSON trajectories.
8. Compare predictions to the human gold standard.
9. Calculate per-class precision, recall, and F1 plus resource usage.
10. Optionally connect a programming agent through MCP and evaluate repair cycles.

## 14. Compact mental model

```text
Requirement + acceptance criteria + test data + screenshot
    -> multimodal reasoning
    -> GUI action
    -> new screenshot
    -> repeat until evidence is sufficient
    -> criterion judgments + evidence + actionable feedback
    -> human review or coding-agent repair
```

## 15. Glossary

- **GUI:** Graphical user interface.
- **MLLM:** Multimodal large language model capable of processing visual and textual input.
- **Acceptance criterion:** An individually testable condition contributing to a requirement.
- **Trajectory:** Ordered sequence of screenshots, reasoning, and actions.
- **CUA:** Computer-use agent/model used to interact with a GUI.
- **MCP:** Model Context Protocol, used here to connect external programming agents.
- **Xvfb:** Virtual framebuffer that runs graphical sessions without a physical display.
- **Partially met:** Some but not all acceptance criteria are met.
